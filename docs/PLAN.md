# scrollback: plan

scrollback is a native desktop app (Rust + GPUI) that backs up, archives and reads coding-agent transcripts. It pulls transcripts from the locations the owner defines (this machine, a WSL distro, a host over SSH) into an archive it owns, and reads only from that archive. Claude Code is the first agent supported. Windows is the main platform, with first-class WSL; macOS is supported.

- **Feature set:** [FEATURES.md](FEATURES.md). This plan covers how.
- **Visual spec:** [DESIGN.md](DESIGN.md) (tokens, layout, materials, screens, keyboard map; cited as `DESIGN §N`), written from concept E on the design canvas. The boards' sources are the `E-*.dc.html` files in `design/project/`; where a board and DESIGN.md disagree, DESIGN.md wins.
- **Status:** plan, written 2026-11-15. Nothing here is built. Decisions marked *(owner)* were made by the owner in the planning conversation; the rest are proposals the owner has seen and not objected to. §14 lists the risks and what is still to be checked. Sections are cited from code and commits as `PLAN §N` / `D<n>`.

Comment and doc rule: code comments explain *what something is and why*, in the present tense, citing `PLAN §N` where a decision is involved. History belongs in commit messages, never in comments.

## 0. Goals and non-goals

**Goals (v1)**

1. Back up every Claude Code transcript from this machine, from WSL distros and from SSH hosts into one archive, and keep doing so incrementally (§5, §6).
2. Never lose archived bytes to a sync: appends extend a version, any other change starts a new one, deletions at the source are not propagated (§4). Only the owner deletes from the archive, and that never reaches a location (§4.5).
3. File sessions into the owner's folders automatically by project path, across locations (§8).
4. Read a session comfortably: rendered markdown, tool calls as compact rows that expand, subagents nested, long sessions fast (§9).
5. Find a session again: search across the archive, filters on a folder (§10).
6. WSL distros are first-class locations on Windows: discovered, named, synced without a path typed by hand (§6.3).
7. Hermetic automated testing: generated transcript trees, a loopback shell transport, GUI scenarios (§12).
8. Adding another agent is adding one provider, whether the agent keeps files or a database. Nothing else in the app knows an agent (D8, §7).

**Non-goals (v1):** providers for agents other than Claude Code (the seam for them is built and tested, §7.6), continuing or resuming sessions, writing to an agent's directories, a server or cloud sync, merging archives, encryption, a headless CLI. FEATURES.md lists what is deferred to later and what is out of scope.

## 1. Decisions

### D1. UI stack: `gpui-pre` + `gpui-component` 0.9, exact pins, as the sibling apps *(owner)*
`gpui = { package = "gpui-pre", version = "=0.3.11" }`, `gpui-component =0.9.0`, declared once in `[workspace.dependencies]` and bumped together. toolbox-rs owns the pin, so a bump starts there. Same stack as dv, fc, slide and folio means toolbox-rs's crates and the siblings' lessons carry over.

### D2. Locations, not a server *(owner)*
One app owns the archive on the machine it runs on and pulls from locations: Local, WSL, SSH. There is no daemon, no protocol and no accounts. The archive and sync logic live in a gpui-free crate (§3), so a headless sync or a server mode can be added later without redoing storage.

### D3. The archive is plain files plus a SQLite catalogue, in one folder *(owner: no setup)*
The archive is created in the app's data directory on first run, without asking, so the app works as it is on any machine; Settings can point it at a different folder. Transcript bytes are stored as write-once, compressed files under the archive folder; the catalogue (which bytes belong to which source file and version, plus the owner's folders and stars) is a SQLite database in the same folder, through `toolbox_store` with its checked backups (§4). One folder to move, copy or back up. Each archived file also carries a small manifest naming its source, so the transcripts can be recovered without the database.

### D4. Versions are append-aware; nothing is overwritten *(owner: versioning; the mechanism is proposed)*
An item's bytes are stored as segments (an item is a file, for an agent that keeps files; §7.1). New bytes appended at the source become a new segment of the current version. Anything else (earlier bytes changed, the file shrank, it was replaced) starts a new version from offset 0. Existing segments are never modified or deleted by a sync (§4.2, §5).

### D5. Raw bytes in, parse on read
The archive stores exactly what the source held: a file's bytes, or for an agent that keeps a database, a lossless export of its records (§7.2). The session index (titles, project paths, counts, search text) is derived by parsing, carries the parser's version, and is rebuilt when the parser changes (§7). Unknown line types and unknown tools are kept and shown generically, never dropped.

### D6. One shell transport for WSL and SSH; nothing installed remotely
A WSL distro and an SSH host are both "a POSIX shell reached through a child process": `wsl.exe -d <distro> --exec sh -s` and `ssh <host> sh -s`. One implementation with two launchers lists and reads files with standard tools (§6.2). dv's precedent is a Linux backend binary installed in the distro (dv D6); scrollback's sync is batch work that doesn't need one. If the shell approach proves fragile across real hosts, a helper binary behind the same `Transport` trait is the fallback.

### D7. `wsl.exe` and `ssh` are shelled out to
Both run through `toolbox_process` (no console window, a process tree of its own, back-pressure). `ssh` runs with `BatchMode=yes` and a connect timeout: it uses the owner's config, keys and agent, and fails instead of prompting. scrollback stores no credentials.

### D8. Agent-agnostic: everything about an agent is in its provider; Claude Code first *(owner)*
The archive, the sync engine, filing, search and the reader know only items, sessions and the common transcript model. A provider supplies everything specific to an agent: whether it is present at a location, how to enumerate and fetch its data through a transport, which items make a session, and how to parse them (§7). Agents don't all keep flat files as Claude Code does; some keep a database. So fetching belongs to the provider and not to the sync engine, with shared helpers for the two common shapes (§7.2). v1 ships one provider, Claude Code, plus a test-only provider backed by SQLite that keeps the seam honest (§12). Nothing outside `provider/claude_code` knows Claude Code's format, and adding an agent changes nothing outside its provider (§7.6).

### D9. A session's project path is its first working directory
Claude Code records `cwd` on each record. The project path is the first one in the main transcript, which is also what the transcript's directory name encodes (lossily). Sessions move between directories as they run; only the first counts for filing (§8).

### D10. Search through SQLite FTS5; tool output is not indexed *(owner: tool output)*
`toolbox_store` bundles SQLite with FTS5. The index covers titles, user prompts, assistant text, and tool calls' commands and paths. Tool output, most of a transcript's bytes, is left out for now to keep the index small (§10).

### D11. Markdown: the stack's `TextView`, wrapped *(measured; the owner has not yet seen the result)*
Replies are rendered with the `TextView` that ships with the pinned stack (it lives in `gpui-base`; `gpui-component` re-exports a thinner one), behind a wrapper in `sb_ui::markdown` that applies the theme, feeds it token kinds from our tree-sitter highlighter and adds the code block's header. A spike rendered a generated corpus of every construct and, for numbers only, the real replies on one machine:
- **Coverage:** everything replies contain renders correctly: headings, emphasis, links, nested lists, task lists, quotes, tables, fenced code in a dozen languages, malformed input. Real replies are small (nine in ten under a kilobyte, none over ten) and mostly inline code, bold and lists.
- **It already has what an own renderer would have to write:** selection across blocks, copy, and find highlighting. folio's renderer has none of those, nor tables, and its provenance would need clearing first; adapting it was estimated at several times the work.
- **Rules that follow:** keep parsed states only for replies near the viewport (a state held per reply costs about half a megabyte and slows frames); sanitise raw HTML and resolve images ourselves before real transcripts are shown, as dv does.
- **Known gaps, accepted unless the owner objects:** the code header's language label sits at the right beside Copy; no horizontal scroll in code (long lines clip or wrap); nested ordered lists are lettered; a link's underline colour and the find mark's style can't be set; a selection is lost when its row scrolls far out of view. Closing them means patching the stack or getting options accepted upstream.
- **Hardened since:** a piece reaches the view only if the view's own parse of it, timed off the UI thread, stays within 8 ms per 4 KiB, and the view's code highlighter is replaced by the reader's bounded one (§9).
- **Unmeasured:** Windows, and the large bodies likely in the bigger archive (web-fetch results, compaction summaries, pasted prompts). A body of about 100 KB takes about 100 ms to lay out and several milliseconds a frame while visible.

### D12. Layout: concept E *(owner)*
A's sidebar (library rows, folder tree, locations at the foot) is always present; the main area is B's folder page or B's reader, without the timeline gutter. A 40 px title bar with global search; no status bar (§11).

### D13. The theme is a module of the app for now
toolbox-rs has no shared tokens or components yet (`gpui_theme_kit` is scaffolding only). scrollback carries its own theme module as the siblings do, with `gpui_appearance` for light/dark and window materials.

### D14. Deleting is the owner's act, and stays in the archive *(owner)*
A session can be deleted from the archive. It goes to Trash first and can be restored; deleting it for good removes its stored bytes and leaves a tombstone, so a later sync doesn't archive it again while it still exists at its location (§4.5). Deleting for good removes the session's conversation: every copy of it and the same session archived from another location go with it, and none of it is archived again from any location (§4.5, §7.7). Only what is in Trash is deleted for good: the same session from another location, shown in the library on its own, goes to Trash first; a copy hidden behind its original is shown nowhere and goes with it. No delete ever reaches a location (D6: the transports have no write operation).

### D15. Licence: MIT; lift from the siblings, except what they took from GPL sources *(owner)*
The sibling apps are the owner's, so their code can be lifted and relicensed here. dv and toolbox-rs are already MIT. fc and slide are GPL-3.0 because they carry copies of Zed's `sqlez`; that code, and anything else in a sibling that came from a GPL project, is not the owner's to relicense and stays out. scrollback never needs `sqlez`: its database layer is `toolbox_store`, the MIT crate on rusqlite that toolbox-rs built to replace it (D3). The limit only matters when lifting other code from those apps, so check where a file came from before lifting it.

### D16. Packaging and updates: Velopack, as dv (its D9)
- **Packages.** `vpk pack` (vpk 1.2.161) makes a one-click per-user `Setup.exe` on Windows (no wizard, no admin) and a `.pkg` on macOS (arm64), plus full and delta update packages and a release feed, from the shipped shape (`-p scrollback --no-default-features`, no automation) built with the `dist` profile. `script/package` makes a trial; the release workflow makes the published release.
- **The pack id is `scrollback-app`, never `scrollback`.** Velopack owns `%LOCALAPPDATA%\<pack id>` and deletes it on uninstall, while the data folder with the archive is `%LOCALAPPDATA%\scrollback`; a test keeps the two apart, and Settings refuses to put an archive under Velopack's install root. Updates replace only the installed program (`current\`, or the app bundle on macOS).
- **In the app.** `installer::run()` is first in `main`, in a packaged build only, with no hooks of scrollback's own. The updates service checks the feed baked in at build time (`SCROLLBACK_UPDATE_FEED`) 10 s after start and every 4 h, with a watchdog on a stalled check, and downloads in the background. Settings shows "scrollback X is ready" under the version with **Restart to update**, which asks first as Quit does and then hands over to Velopack's updater, which waits for the app to exit. An update is never applied by itself at start-up. Startup errors and panics on the windowless Windows build go to a message box and `crash.log` in the data folder.
- **Off** in a development build, under automation, with `--data-dir`/`SCROLLBACK_DATA_DIR`, and in a copy that isn't installed. Velopack writes only in its own packages folder and keeps no log.
- **Signing.** None on Windows yet (SmartScreen asks once). macOS is ad-hoc sealed unless the repository variable `MACOS_SIGNING` is on: then Developer ID signing and notarization run in the `release` environment, on a binary built in an unprivileged job.
- **Feed.** A release build bakes the GitHub Releases feed of this repository, which installed copies read anonymously, so the repository is public; the repository variable `UPDATE_FEED` overrides it. A build made with no feed (`script/package --no-feed`) has its updater off, and Settings says updates aren't set up for this build. The release reads the repository with the workflow's token, and provenance attestation runs only while the repository is public.

## 2. Concept model

### 2.1 Entities

| Entity | What it is | Identity |
|---|---|---|
| Archive | The folder scrollback owns: stored bytes, catalogue, backups | An id written at creation (`archive.json`) |
| Location | A place to pull from: Local, WSL distro, SSH host | An id fixed at creation, independent of its display name |
| Provider | The code for one agent (Claude Code) | A fixed id |
| Item | One unit a provider archives at a location: a file, or an export of a database's records (§7.2) | Location + provider + the provider's key for it (a file's path relative to the agent's root) |
| Version | One continuous history of an item's bytes | Item + number, from 1 |
| Segment | One stored byte range of a version | Version + offset |
| Session | A conversation: a main transcript and the items that belong to it | Location + provider + the provider's session id |
| Folder | The owner's grouping of sessions; folders nest | An id |
| Attached path | A project path on a folder, optionally limited to one location | Folder + normalised path + location |

### 2.2 What is derived and what is not

- **Authoritative, written by sync:** locations, items, versions, segments. Losing these loses the mapping from stored bytes to sources; the per-file manifests (§4.1) allow rebuilding them.
- **Authoritative, written by the owner:** folders, attached paths, a session's folder when filed by hand, stars, which version is the reading copy, what is in Trash, and the tombstones of sessions deleted for good. Only the database and its backups hold these.
- **Derived, rebuildable:** sessions' parsed fields (title, project path, times, models, branch, counts, tokens), the search index, rule-filed folder assignments, and what the records an app keeps beside its copies say of where each ran, with the location this machine's `ssh` makes of it (§7.7).

Owner state is keyed by session identity, not by a derived row's id, so a reindex can drop and rebuild every derived table.

### 2.3 Invariants

1. A sync writes new files and new rows. It never modifies or deletes a stored segment.
2. A segment is recorded in the catalogue only after it is durable on disk.
3. An item missing at the source is marked gone, with the time it was first seen missing. Its versions stay.
4. Reading never touches a location. Every view is served from the archive.
5. Nothing is ever written to a location, and nothing is ever deleted there.
6. Stored bytes are removed only when the owner deletes a session for good (§4.5).

## 4. The archive

### 4.1 On disk

```
<archive>/
  archive.json                    format version, archive id, created
  scrollback.db                   catalogue and index (toolbox_store)
  backups/                        toolbox_store's checked backups of the database
  lock                            held while an app has the archive open
  tmp/                            in-flight writes; emptied on start
  orphans/                        files that were under files/ without a catalogue record, set aside
  files/<location-id>/<provider>/<ab>/<item-id>/
      source.json                 provider, location, the item's key
      v0001/0000000000000000.zst  bytes [0, a) of version 1
      v0001/0000000000184467.zst  bytes [a, b): an append
      v0002/0000000000000000.zst  the source was rewritten: version 2 starts at 0
```

- **`<item-id>`** is the first 32 hex digits of the SHA-256 of the item's key; `<ab>` is its first two digits. Keys, which for files are source paths, are not mirrored on disk: Claude Code's project directory names alone run past 170 characters, which with the archive's own prefix exceeds Windows' 260-character limit, and Linux paths can hold characters NTFS rejects. `source.json` keeps the original path, so the tree is still recoverable without the database.
- **A segment** is the zstd-compressed bytes of one range, named by its 16-digit offset. A version's content is its segments decompressed in order. A segment's uncompressed size is capped, so a large range is stored as several and a read can start at any offset by opening the segment that holds it.
- **Writing a segment:** write to `tmp/`, flush to disk, rename into place, then record it in the catalogue in one transaction. A crash before the transaction leaves an uncatalogued file, and nothing goes looking for it at a start (a start only empties `tmp/`). When a later pass places a segment at that path, a file in the way that the catalogue doesn't record is kept if it is byte-identical to the new segment, and moved to `orphans/` under the same path if it differs; so a killed pass leaves nothing behind once it is retried, and after a catalogue is restored from an older backup the segments stored since are adopted again wherever the source still has the same bytes. A file the catalogue records is never touched or replaced. Verify reports what is left unrecorded (§4.4), and the owner can have it set aside.
- **The transport hashes in request order.** The snapshot proof (§7.2) depends on it, so every transport must keep it.
- **Hashes:** the catalogue stores the SHA-256 of each segment's uncompressed bytes and of each version's content up to its current length. SHA-256, because a remote can compute it with standard tools (§6.2).

### 4.2 Versions

Given the archived length `L` and hash `H` of the current version, and the source's size `S`:

| Source | Plan | The proof decides |
|---|---|---|
| Size and modification time unchanged | Unchanged: skip | |
| `S > L` | Fetch `[L, S)` | The source's hash of `[0, S)` equals the archived prefix plus the fetched bytes: **appended**, a new segment of the current version. Otherwise fetch the whole file as version n+1: **rewritten** |
| `S == L`, time changed | Fetch nothing | The source's hash of `[0, L)` is `H`: **touched**, record the new time. Otherwise fetch the whole file as version n+1: **rewritten** |
| `S < L` | Fetch the whole file as version n+1 | **Shrank** |
| Not present | | Deleted at the source: mark gone; keep everything |

- **Planning reads nothing at the source.** It compares the scan with the catalogue. Every range that is fetched is then proven: after it is read, the source is asked for the hash of everything up to the range's end, and the range is stored only if that equals the hash of what the version would then hold. Size and modification time decide what to look at; only the hash decides what is stored.
- **A file modified within two seconds of the scan** is given a stamp marked fresh, which never equals the stamp a later scan gives it once it has aged, so it is looked at once more rather than trusted as unchanged.
- **The table is the same for an item that isn't a file.** Its provider gives it a length, a stamp and a way to read a range (§7.1), so records appended to a database-backed session extend its version just as appended lines extend a file's (§7.2).
- **A line has a bound.** A line-oriented item whose unfinished last line passes 32 MiB is stored as far as it goes and proven like any other item, so no file can make a pass hold gigabytes in memory.
- **Line-oriented items (JSONL) are cut at the last newline while they are changing.** A transcript being written may end mid-record; the tail after the last `\n` is left for the next sync. When a later pass finds the item with the size and stamp it had before, the tail has settled and is stored too, so a file that never gets its final newline is still archived whole. A stored version can therefore end mid-line, and parsers tolerate it (§7.5). Other items are taken whole.
- **A version only ever holds bytes the source held at one instant.** That is what the proof above enforces. An item whose proof fails because it was changing under the pass is deferred to the next one, and the catalogue records which items are waiting and since when.
- **Versions belong to items, not sessions.** The version number the reader shows for a session is its main transcript's. The session's other items (subagent transcripts, saved tool results) version on their own.
- **Held back.** Only transcripts (a session's own and its subagents') can be held back; for any other item the newest version is the one read. A new version of a transcript is held back when it is shorter than the reading copy (the newest version that is not itself held back), or parses worse than it: it has fewer recognised blocks over all branches. An append can therefore never be held, and damage in the archive is not a parsing matter (verify and the refetch deal with it, §4.4). The reading copy stays, and the newer version is flagged for the owner (FEATURES: Versions). A hold for parsing is recorded apart from a hold for length. Storing never lifts a hold: an append to a held version leaves it held, and the index lifts it once the version is no shorter than the copy before it and parses no worse. A read that failed, or damage in the archive, never decides a hold.
- **The owner's choice** is per item. Choosing a held-back version accepts it: its hold is cleared for good and later versions follow the rule as usual (if the rule would still read another version, the acceptance also acts as a pin). Choosing an older version pins it until a version arrives that is newer than any that existed when the choice was made, or until the pinned version is found damaged; then the pin lapses. A damaged version can't be chosen.
- **Reading a version for a look** chooses nothing: `Archive::session_at` reads a session with one item pinned to a version, and `Catalogue::history` lists an item's versions (why each started, how many syncs extended it, the reading copy, whether the owner chose it). "Make vN the reading copy" sets the choice and re-indexes the session.
- **Each version records why it started:** first sync, rewritten, shrank, replaced (the item was gone and came back with other content, or its export format changed), refetched (the version before it was found damaged, §4.4).

### 4.3 Catalogue

Tables, in outline (the schema is `toolbox_store` migrations, append-only):

| Table | Holds |
|---|---|
| `location` | id, kind, name, connection details (distro, or SSH host), its drive mount when it has its own, last sync attempt and success, last error, unreachable since and why, removed-at (a removed location syncs no more and keeps what was archived from it; adding it again clears it) |
| `location_check` | per location: its last connection test (when, the sh that answered, the login shell if it answered, the tools it lacks, how long it took); written at each test and when a place is added straight after a passing one, not at syncs |
| `location_provider` | per provider found at a location: the retention last read, and the root where it keeps its data there, from the last pass |
| `item` | location, provider, key, item id, kind (transcript, subagent, tool result, sidecar, register: what an agent's app keeps about its sessions as a whole, of no one session, §7.7), the session it belongs to, last seen length and stamp, gone-since |
| `version` | item, number, reason, started, length, hash, held-back, held for parsing, accepted by the owner, damaged, the provider's export version when the item is an export |
| `segment` | version, offset, length, hash, stored-at |
| `folder` | id, parent, name (unique among siblings ignoring case; controls and invisible characters removed, since a name can come from a project path), position |
| `folder_path` | folder, normalised path, the path as typed, location (nullable) |
| `session_state` | session identity → folder, filed-by (rule or hand), starred, trashed-at (phase 6). Keyed by identity, never by the derived row, so it survives a rebuild of the index |
| `reading_choice` | item → the version the owner chose to read; removed when a newer version of the item starts (§4.2) |
| `tombstone` | a session deleted for good: its identity, when it was deleted, its project path and when it ran (so Settings can name it), and the keys of the items it had. Nothing taken from the conversation, not even its title |
| `removal` | files still to be removed after a delete for good: the item folder, version and offset, with the segment's length and hash |
| `session` *(derived)* | session identity, main item, title, project path, first and last timestamp, models, branch, entrypoint, counts, tokens, parser version; the agent's id for the conversation and, for a copy kept by another app, the provider's words for it (§7.7) |
| `copy_record` *(derived)* | per location, provider and conversation: what the records an app keeps there say of where the conversation ran (the host as the app recorded it, the transcript's path on that machine), read from the location's register items; and from the last attribution, whether this machine's `ssh` resolved the host and the location it is the same place as (§7.7) |
| `search.db` *(derived, a separate file)* | the search spans and their index (§10) |
| `kv` | settings that belong to the archive: `sync.stale_after_days`; `verify.last` (a versioned record: when, how long, counts, and the first 200 damaged versions) |

### 4.4 Opening, locking, verify

- The archive defaults to a folder in the app's data directory, created on first run (D3). Its path is a setting, kept outside the archive. If the folder can't be reached (an unplugged drive, a changed letter), the app says so and offers to locate it; it never creates a fresh archive silently in its place.
- `lock` stops a second app from opening the same archive for writing.
- **An archive folder without its database is not opened as empty.** Opening fails and names the newest backup in `backups/`; a missing `archive.json` means the folder is not an archive.
- **Pointing the app at a different folder** opens the archive there, or creates one if the folder is empty (system files such as `.DS_Store`, `Thumbs.db`, `desktop.ini` and `._*` aside); a folder holding anything else is refused, and so is a folder on a network drive (SMB, NFS, WebDAV, AFP: `statfs`'s file system name on macOS, a share or `GetDriveTypeW`'s `DRIVE_REMOTE` on Windows), where SQLite's write-ahead log isn't safe. A folder a cloud service keeps in step (OneDrive, Dropbox, iCloud Drive, Google Drive, by their folders' names) is allowed, and the question warns that the archive changes often and the service can make conflicting copies of it. A removable drive is fine. No archive is made inside another archive, or around one. It moves nothing; **Move…** does (below).
- **Only the default folder is created without asking.** A chosen folder that later holds no archive is reported unavailable, never replaced. Switching stops every pass, index, verify and re-fetch on the open archive, waits until nothing runs, then rebuilds the services over the other one; the archive left behind is closed and never written again.
- **App settings** (the archive folder and the last archive opened, theme, material, sync interval) live in `settings.json` in the app's data folder, written through a temporary file and a rename; one that can't be read (not JSON, a newer version, an archive folder that isn't a full path) is never written over, and nothing is opened or made until the owner chooses the default archive or another folder. Archive-scoped settings live in the catalogue's `kv`.
- **Moving the archive** (Settings › Move…; `sb_core::archive::relocate`, lifted from folio's `folio_core::relocate`, D15) copies the archive into another folder and moves the app onto the copy. The old folder is only ever read: nothing in it is changed, moved or deleted, then or later, and the app never offers to delete it.
  - **Refused**, in words and before anything is made: a folder that holds anything (system files aside, as above); the archive's own folder, one inside it or one that holds it; one inside another archive or holding one; one inside the installer's (D16); one on a network drive (as above); a file; a folder that can't be written; a volume without room. Room is estimated up front: what the move copies, the catalogue and the search index as big as they are here (the new archive makes its index again), and a twentieth more for what syncs add meanwhile, against the free space of the volume the folder is on (`statvfs`, `GetDiskFreeSpaceExW`). The confirmation says both, and warns of a cloud service as above.
  - **Copy**, while the app runs and syncs go on: every file but the catalogue and its journals, `search.db`, `tmp/` and `lock` (links are neither followed nor copied), each hashed as it is read and its copy read back and hashed again, which must match; a segment's read-back is checked against the catalogue on the way, decompressed. The read-back may come from the system's cache, so it proves what was written, not the drive's surface; the Verify after the move reads it all again. It goes through the handle the copy was written with, so a file is opened twice, not four times: on Windows the antivirus scans each file written again at each open. Each copy is written in the new folder's `tmp/`, flushed and moved into place there. Several files are copied at once (8 on Windows, where the time goes in each file's flush and scan; 4 elsewhere, where APFS puts each file's creation and rename one after another and more only contend), each with all of the above; a stop or a failure stops every copy at its next file, or its next read, before what was made is removed. Flushing in batches would be as safe from a crash, since nothing in the new folder is used before the commit and a crash before it removes the copy whole, but it would flush as many files, which is the cost. The progress weighs files and bytes together, a file as a quarter megabyte besides its own bytes: by bytes alone the catalogue's backups, copied first, filled most of the bar while thousands of small segments waited. Segments are write-once, so a copy stays right; a file that goes meanwhile (a delete for good) is passed over. The files an operating system leaves in a folder (`.DS_Store`, `Thumbs.db`, `desktop.ini`, `._*`) are each folder's own at the top: never copied, never named in the marker, never removed.
  - **Finish.** The services over the archive close as a switch closes them: passes, indexes, re-fetches, verify and measures stop and nothing new starts; the owner's changes made meanwhile wait, and are written to whichever archive the services come back over. Changes that don't wait are refused while a move runs, saying "Wait for the move to finish.": locations added, renamed or removed, Stale after, a tombstone allowed again or put back, Fetch again. Once nothing runs, the background removal is held (first: it takes `placing` for each item) and then `placing`, so no segment is between its place and its commit. Then, under the old folder's lock, held all along: the catalogue is copied with `VACUUM INTO` (toolbox_store's checked copy, `integrity_check`), and its tables' row counts must equal the old one's; files added or changed since the copy (by size and modification time) are copied, and copies of files gone since are removed; every segment the copied catalogue records is checked against its hash, decompressed (those checked during the copy and unchanged since count); `archive.json` goes last, and the copy is opened as an archive. Then the settings file's `archive` names the new folder, in one atomic, flushed write: the point of no return. Only then is the marker taken away, do the services start over the new archive, with the owner's waiting changes, and does a Verify of it run. Quitting or closing the window during the finish waits for it, a matter of seconds, and quits once it is over, before that Verify ends; a stopped verify keeps nothing, so a start that finds the archive where `moved` says it went and no verify ended since the move runs it then, in the background, as the move's own.
  - **`search.db` is rebuilt, not copied.** It is derived, and the new archive rebuilds it at its first index (§10), as when the file is gone. A consistent copy would have to be taken in the pause, which would last as long as the index is large.
  - **Pause, not retake.** folio takes its database copy again when a write landed while it was taken. Here a sync writes the catalogue every few seconds, so a retake can keep failing, and it wouldn't stop a sync, verify, re-fetch, removal or index writing to the old folder after the copy. Closing the services as a switch does stops all of them, so the copy is exact. Syncs go on through the copy of the files, which is nearly all of the time; the pause is the finish alone.
  - **Stop, or a failure,** leaves the archive where it was, and the services go on over it (made again over it if the finish had closed them). What the move made in the new folder is removed: the entries its marker names (the archive's own, copied) and those an archive has, then the marker, and the folder itself when the move made it. So the folder is as the owner chose it, and trying again isn't refused as not empty; anything else there is left. What another program holds stays, and Settings says so. A folder the settings file names is never removed: a write of it that failed after its file was in place named the copy all the same, and the copy is then the archive in use.
  - **Crash safety.** The settings file names one archive at any time. It gains `move` (`{"v": 1, "id", "from", "to", "made", "started"}`, `made` when the move makes the folder) before anything is made in the new folder, and loses it in the same write that points `archive` at the new folder and adds `moved` (`{"v": 1, "from", "to", "at"}`), which says where the old copy is until the owner dismisses it. That write is `sb_core::archive::write_durably`: a temporary file moved over the file (tried again for a moment while another program holds either), then the file and its folder flushed; it counts as written once the move has happened, since every reader finds the new file from then on, and a flush that fails after it is said in the log. A start that finds `move` was cut short before the point of no return: it opens the old archive, which nothing changed, abandons the move and says so in Settings, and removes the partial copy the same way a stop does when the new folder still holds the move's marker (`moving.json`, naming the move's id). A move cut short before its marker leaves at most its lock and an empty `tmp/`, which go, with the folder when the move made it; Settings then says nothing had been copied. A folder holding anything else is left as it is, and Settings says so. A start after the point of no return finds `archive` on the new folder and nothing pending, and takes away the marker if the crash came before the move did. So no whole copy is ever left that nothing uses. A `move` that can't be read (not an object, a newer `v`, a folder that isn't a full path) makes the file unreadable, as `archive` does; a `moved` that can't be read is forgotten.
  - **The locks.** The old folder's is held throughout (the app has it open). The new folder's `lock` is taken before the first file is copied and passes to the archive opened there, so no scrollback opens or makes an archive in either folder meanwhile; until `archive.json` is there the new folder holds no archive anyway, and Use a different folder… refuses it as holding other files.
  - **Windows.** Files are copied, never renamed across volumes. A move within the new folder is `MoveFileExW` with `MOVEFILE_WRITE_THROUGH` and without `MOVEFILE_REPLACE_EXISTING`, through a `\\?\` path when the path is long; std's own calls take long paths already. Paths come in without that prefix (`sb_core::archive::plain`): the folder picker gives a long one with it, and a settings file an earlier version wrote may hold one, which is read without it. They are kept, compared and shown so, and only a call of Windows' own is given one. The settings file's move replaces with `MOVEFILE_WRITE_THROUGH`, then the file is flushed (`FlushFileBuffers`) and so is its folder, through a handle opened with `FILE_FLAG_BACKUP_SEMANTICS` (a volume that refuses a folder's flush has had the write-through move); so are the new folder's when its marker is written and taken away. A file Windows keeps refusing (another program holds it, an antivirus scan say, or its permissions) is tried again for a moment, then fails the move, naming it.
- **Verify** re-hashes every segment against the catalogue and every version's running hash, and reports mismatches, missing files and files under `files/` that the catalogue doesn't record, which the owner can then have moved to `orphans/`. It repairs nothing in the archive by itself (the one thing it rebuilds is the search index, which is derived): it marks each damaged version (a missing segment, one that doesn't decode, or a hash mismatch; a read error alone marks nothing). The next sync fetches an item whose newest version is damaged whole, as a new version, when the item still exists at its location; **Fetch again from its location** runs that for one item at once. Otherwise the version stays marked and readable as far as it decodes. Reading a version checks each segment against the catalogue as it goes and fails rather than return wrong bytes.

### 4.5 Deleting

- **Delete** moves a session to Trash: `session_state.trashed-at` is set. Its bytes stay, sync keeps archiving its files, and it disappears from every view except Trash. **Restore** clears the mark and returns the session to its folder; if that folder was deleted meanwhile, the session goes to Unsorted and the filing rules run on it (§8).
- **Delete for good** (from Trash, after a confirmation that names the session and what it holds) removes exactly what the confirmation showed: the session's items under `files/`, their catalogue rows, its derived rows and its search text, and writes a tombstone in the same transaction as the rows. If the session changed while the confirmation was open, the delete is refused and the owner is shown the new numbers. It is refused while the session's location is syncing. A location is never touched.
- **Files are removed after the commit,** each only while it still holds the bytes the catalogue recorded (its length and hash), together with any copies of the session's items set aside under `orphans/`. Removals that could not be done (a file another program holds open) stay recorded as pending, are reported to the caller and by verify as waiting, are never set aside, and are finished in the background, by the delete itself or at the next start. Opening the archive never waits for them; the day's catalogue backup does, so no backup holds a removal still to do.
- **Deleted text is really gone:** a deleted session's text leaves the search database at once, so nothing finds it; both databases overwrite what a write frees (SQLite's `secure_delete`, on every connection that writes) and their write-ahead logs are truncated after a delete. That leaves two kinds of trace in the files, which the background removal then erases. Each step, and what it guarantees:
  - `secure_delete` overwrites the cells a delete takes out, and the pages it lets go of. It doesn't reach a copy of a cell a rebalance left in the unused middle of a page it rebuilt (SQLite's `rebuildPage` leaves that gap as it was), so deleted text can stay inside pages still in use.
  - The search index's entries of the session's text are marked deleted rather than taken out (§10). Compacting the index (FTS5 `rebuild`) makes it again from the spans there are, without them.
  - `VACUUM` then writes each database anew, page by page from what it holds, so no page keeps a copy of anything deleted: the search index after its compaction, the catalogue on its own connection. It builds the copy aside and then writes it back through the database's log. The search index's copy is a file in SQLite's temporary folder, which is the system's (`%TEMP%` on Windows; on macOS and Linux `SQLITE_TMPDIR`, else `TMPDIR`, else `/var/tmp` or `/tmp`), not the archive's folder: **for the moment it takes, the search index's live text (never the deleted text, which the compaction took out first) is in a file in the system's temporary folder**, which SQLite deletes as it closes it. The owner accepted this. The catalogue's copy is made in memory, as it is small.
  - The catalogue's `VACUUM` is done only while the catalogue is under 128 MB, which it writes anew in about a second: it never waits on a write (it tries again a moment later, for ten seconds at most) and no write waits on it long enough to give up. A larger one (tens of thousands of sessions) is left for the next start, and tried once a start, not after every index; meanwhile it is said, as below, as too large to compact here.
  - Both logs are then truncated, so nothing of the old pages is in them.
  - **What proves it:** a test reads both databases and their logs byte by byte after a delete for good and finds nothing of it; it fails without the compaction, or without `secure_delete` on either database. It doesn't reach the rebalance residue, which takes particular page splits to leave (a standalone reproduction found it in 5 of 31 seeds of the span table's delete-and-insert pattern); `VACUUM` is there for that.
  - **What it takes:** on an archive of a few thousand sessions, a few seconds. Room, which it checks first: on the archive's disk, three times the index's entries (a new copy, in the log and then the database, and the overwritten pages of the old one in the log), the search database once more (`VACUUM`'s pages in its log) and the catalogue once (its pages in its log); on the system's disk, where SQLite's temporary folder is, the search database once (`VACUUM`'s copy). When the two are the same disk, all of it there. Searches go on meanwhile. Text an index would write is left to the backlog instead (§10), so rows never wait; text the backlog's index writes, and a forget, wait. Quitting, switching archives, a move's finish and a cancelled index stop it at once, the catalogue's `VACUUM` too (SQLite's interrupt), with nothing changed. The compaction an index does when much of the index is marked (§10) is the same `rebuild`, without `VACUUM`: text replaced there is still in the archive.
  - **What fails, and what then:** the delete for good marks the catalogue in its own transaction, once for each database, and each mark is taken off only once that database is done (the search index compacted and written anew, the catalogue written anew, each log truncated). A crash, a stop, too little room, a write holding the catalogue all along, or a read holding a log leaves that database's mark for the next try, at the end of every index and at every start, and the other database is not done again for it. A read that holds a log when the scrub comes to it costs it a fifth of a second: it looks first, and leaves that database for later before doing any of its work, so a delete for good, which waits a moment on each log itself, is never held up longer by the scrub after it. A mark that stays is said as a note in Trash and in Verify's last result (DESIGN §4.8, §4.13): with the room it waits for and on which disk, the archive's or the system's, when that is it, or that the catalogue is too large to compact here. A move erases it before it copies anything. The day's catalogue backup is taken after it, and is written anew (`VACUUM INTO`), so it holds nothing a delete freed either. What remains by design is the tombstone (the project path and dates, no title and no text), and catalogue backups made before the delete, which hold the session's title, the start of its first prompt and its project path until they age out. A removal decides by the catalogue: everything in a deleted item's folder goes unless the catalogue records an item there again.
- **A tombstoned session's items are skipped by sync** (§5), so deleting isn't undone by the next pass while the session still exists at its location: a scanned item is dropped when its key was deleted, or when its session is a deleted one, unless the archive holds that session again. New items that appear later under a deleted session are skipped too. Each pass reports the deleted sessions it met, so the owner can be told that a session they resumed is not being backed up.
- **Deleting for good removes the conversation, wherever it is archived** (§7.7). The other sessions of the session's conversation go with it: its copies kept elsewhere, and the same session archived from another location. Each gets its own tombstone, in the same transaction, and the confirmation names them (DESIGN §4.8); otherwise the delete would bring the session straight back as its copy. It is refused while the same session from another location is out of Trash (it is shown on its own, so the owner moves it to Trash first; D14), while any of their locations is syncing, while any row of the provider at the same project path was made by an older index or parser, or is to be read again because its items could not be read (it may not say which conversation it is: during the backlog an upgrade starts), and while it or one of them holds more than one transcript of its own, of which only the first is read.
- **No location archives a deleted conversation again.** A tombstone keeps the conversation's identity (the provider, the agent's id for it, its project path) beside the session's. An index that meets a session of a tombstoned conversation (a copy synced after its original was deleted, an original from a machine added after its copy was deleted, a row the backlog makes again) deletes it for good in the same transaction, as its key would have been skipped, and the archive removes its files; the index's report counts it (`IndexReport::deleted`), as a pass counts what it skips. Deleting a lone copy so deletes its original before it is ever archived, and the confirmation says so. Deleting a copy for good also deletes the app's records of its session (its register items, `copy_record.sources`) and its `copy_record` row: they are that session's own. An index also deletes for good a copy whose record names, by its path, a transcript the owner deleted for good where it ran (§7.7), so a deleted conversation doesn't come back as a copy matched by its path alone. A session its parser can't read still says its conversation where its provider can tell it from the transcript's key (`Provider::conversation_of`; Claude Code: the transcript's name): a copy never read has no project path to match by, so it is of its conversation whatever the original's path, hidden behind it, named with it when it is deleted, and deleted for good by a tombstone of its conversation. A session resumed under a new id is a new conversation to the agent, with its own id, and is not one the tombstone keeps out. This keeps no more than the tombstone did: the agent's id is an identifier, the path was already kept, and nothing said in the session is. Settings lists a conversation's tombstones under one entry, the copies under their original, and allowing it again allows them all.
- **A session deleted under an earlier classification stays deleted.** When reclassification makes a deleted transcript's key the own transcript of a session that has no other (the desktop app's loose subagent files, which belonged to no session before), the items that session now has are buried with the deleted one.
- **Removing a tombstone** (Settings lists them) lets the next sync archive the session again, if its location still has it.
- Trash is never emptied automatically. A trashed session keeps syncing and being indexed; if a reclassification merges it with another session, the result stays in Trash.

## 5. Sync

One **pass** syncs one location with one provider. The engine drives it and knows nothing about the agent; the provider does the two steps that touch the location, through the location's transport (D8):

1. **Scan** (provider): every item the agent has at the location: its key, kind, session, length, and a stamp that changes when the item does. For a file the stamp is its size and modification time.
2. **Plan** (engine): after the items of tombstoned sessions have been dropped from the scan (§4.5), compare the rest with `item` and decide per item what to fetch (§4.2). Planning touches nothing at the location.
3. **Fetch and prove** (provider), a batch at a time: the planned byte ranges, in one stream, then one request for the source's hash up to the end of each.
4. **Store** (engine): each proven range becomes one or more segments (§4.1); the batch is made durable and its rows are committed in one transaction. A range whose proof fails is not stored: the item is fetched whole as a new version later in the pass, or **deferred** to the next pass if it is still changing.
5. **Index** (engine, with the provider's parser): sessions whose items changed are parsed and indexed (§7.5), and filed (§8). Which sessions are stale is decided from the catalogue, so an index that was cancelled or killed is picked up by the next pass or the next start. It runs whenever the store step ended for any reason but a cancel, after the pass's outcome is recorded. One session that fails to index is recorded and doesn't stop the others, and isn't a failure of the sync.

- **Passes for different locations run in parallel.** One location runs one pass at a time; when it has several agents, their passes follow one another.
- **One item's failure is one item's.** A file that can't be read, a folder that can't be listed and a name that isn't Unicode are reported with the pass; everything else is archived, and nothing under an unlisted folder is marked gone. One provider's failure doesn't stop the others at the location. A pass counts as a success for the location only when nothing failed and nothing has been waiting, deferred pass after pass, for more than a day; otherwise the location keeps its last success and records how many items could not be archived and why.
- **A pass can stop anywhere.** It works in batches (a few hundred items or tens of megabytes), so a cancel, a crash or a dropped connection loses at most the batch in flight. Everything committed stays; the next pass continues from the catalogue. Cancelling is the same as a dropped connection.
- **Triggers:** app start, the owner (one location or all), and an interval while the app is open. Any of them starts a stopped WSL distro to sync it *(owner)*; only listing distros never starts one (§6.3).
- **States** a location shows: synced, syncing (files and bytes done of planned), unreachable (the launcher failed to connect: since when, last success and how long ago), failed (anything else, with the tool's message). Unreachable is not an error and isn't surfaced as one; it is recorded with the location and cleared by the next sync that reaches it. A failure to connect is the location's, recorded once, and what earlier batches stored is kept and indexed.
- **Staleness:** a location with no successful pass for longer than the threshold is flagged. A provider can report how long its agent keeps transcripts at a location (Claude Code: `cleanupPeriodDays`, §7.3), and the flag says how close that is. The value is stored with the location, so an unreachable location uses the one last read.
- **Progress** is reported per pass to the sidebar and the locations sheet: files and bytes done, of the plan, then each step of the index, sessions done of those it has to do (§10).

## 6. Locations and transports

### 6.1 The `Transport` trait

A read-only view of a location's file system, and nothing more. It knows nothing about agents; providers are its only callers (§7).

| Operation | Returns |
|---|---|
| `env(names)` | The location's home directory and the named environment variables |
| `stat(paths)` | Whether each path exists, its size and modification time |
| `list(root)` | Each file under a directory: relative path, size and modification time |
| `hash_prefixes(requests)` | SHA-256 of the first *n* bytes of each requested file |
| `read_ranges(requests, sink)` | The bytes of each requested range, streamed |
| `read_small(path)` | One small file whole (a settings file) |

No operation writes, and none runs an agent's own tools. That is enough for an agent that keeps files, and for one that keeps a SQLite database, whose provider reads the database file through the same operations (§7.2).

- **`LocalTransport`** implements it with `std::fs` on this machine.
- **`ShellTransport`** implements it over a child process (§6.2), with a `Launcher`: `Wsl { distro }`, `Ssh { host }`, and `Command` (a local `sh`, for tests).

### 6.2 The shell transport

- **Each operation is one child process** running `sh -s`. Its stdin carries a fixed script (one function per operation) and then the requests, one quoted function call per line, inside a block that takes its own input from `/dev/null`. The shell has parsed everything before it runs anything, no tool can read the script as input, and nothing but a fixed argument list crosses a command line, so no quoting rule of `wsl.exe`, `ssh` or the remote shell applies. No here-document or temporary file is used; nothing is ever written on the far side.
- **The answer is framed.** It begins at a marker line chosen per call, so anything a login script prints first is skipped, and ends with a terminator; an answer without its end fails the call. Names are NUL-terminated and blocks are counted, so no file's contents or name can be mistaken for the protocol.
- **Listing** uses `find` with batches of `stat`, the far side's own clock, and a second pass that reports folders the user may not read or search. GNU, BSD and busybox `stat` differ; the script recognises which it has from the shape of its output, in one place. A file is taken for missing only when the tool says so in so many words; any other failure makes it unlisted, never gone (§5).
- **Paths that start with `-`** are normal here (Claude Code's project directories all do), so every relative path is prefixed with `./` and every tool gets `--`.
- **Reading ranges:** a block is always exactly the length asked for plus one, the file's bytes followed by a mark and zero padding, so a file that shrinks or vanishes mid-read ends as short or missing and the stream stays in frame. A range inside a large file seeks with `dd` and trims with `tail`. Runs of small whole files are read through one `cat` between two `stat`s; a run that doesn't hold together is asked again file by file.
- **Hashing** uses `sha256sum`, else `shasum -a 256`, over `head -c <n>`, one request after another in order (§4.1). Runs of whole files are hashed by one invocation, each output line checked against its path and each size checked afterwards.
- **The environment** a provider asks for (where an agent keeps its data) is read through the far side's login shell, once per pass, because `wsl.exe --exec` and `ssh host command` don't run profiles. A shell that can't be asked this way (csh, a failing profile) leaves the bare environment. A login shell still starting after five seconds is stopped and the pass fails, rather than looking for the agent in the wrong place. A variable set only for interactive shells is still not seen; the connection test shows which environment answered and the root that was resolved.
- **Calls cut short are run once more.** The whole script sits inside one more pair of braces, so a shell that receives it cut short runs nothing; it then ends with status 0 and no answer, or with a syntax error, and the call is started again once. Separately, an answer whose start arrived but whose end never did, while the launcher ended with status 0 and said nothing (`TransportError::Stopped`), has its call run once more with a warning logged, but only for calls that keep what they read to themselves until the end arrives (`env`, `probe`, `stat`, `list`, `hash_prefixes`, `read_small`), so nothing reaches the caller twice. `read_ranges` hands each range on as it arrives and is never run again; the range it stopped in fails. On WSL under load, about one call in a thousand loses the end of its answer this way, right after the login shell's output; the retry is the fix (owner's decision, §14).
- **Timeouts and cancel:** stopping the pass kills the process tree, and nothing is left running on the far side once the pipe closes. A call that receives nothing for ten minutes is ended as a failure. The script is written from its own thread, so a launcher that is slow to start can still be cancelled.
- **What the remote needs:** `sh`, `find`, `stat`, `head`, `tail`, `dd`, `cat`, `date`, `/dev/zero`, and `sha256sum` or `shasum`. A missing tool is reported by name when the location is added (the connection test) and as the location's failure after that.
- **Cost:** a pass with nothing changed is four processes. A first sync costs under a millisecond per small file in the transport on a local shell; through `wsl.exe` it is to be measured again. One long-lived shell per pass, which would spare SSH a connection per call, is listed for later.

### 6.3 WSL

- **Discovery:** the installed distros and whether each is running, from `wsl.exe --list --verbose` (its output is UTF-16). dv already does this and never starts a stopped distro to list it; its code is the reference.
- **A WSL location is a distro and the distro's default user.** Each provider finds its agent's data inside it (for Claude Code, `$HOME/.claude`), not through a `\\wsl.localhost` path.
- **Adding a stopped distro** doesn't run the connection test, which would start it. It is added as it is, and its first sync starts it.
- **Launch:** `wsl.exe -d <distro> --cd / --exec sh -s`, with `WSL_UTF8=1` so its own messages are readable. Distro names are matched without case, as `wsl.exe` does, and stored as the listing spells them. Docker's and Rancher's utility distros are marked so the UI can leave them out.
- **Path equivalence** for filing (§8): a WSL path under the distro's Windows mount (`/mnt/<letter>/…` by default) is the same project as `<LETTER>:\…`. The mount root comes from the distro's `/etc/wsl.conf` when it sets one; it is read at every sync of a WSL location, and when it changes, the location's project paths and attached paths are read again under the new root and its sessions refiled.

### 6.4 SSH

- **A location is a host string** as the owner would give it to `ssh`: an alias from `~/.ssh/config` or `user@host`. It is checked strictly (`sb_core::location::host_problem`) when a location is added and again before every launch, so nothing typed can reach `ssh` as an option. At most 320 characters, split at the last `@`. A user part takes `[A-Za-z0-9._+-]`. A host part may not start with `-` (nor may the whole string), and takes `[A-Za-z0-9._:-]`, or an IPv6 address in brackets (hex digits, `:` and `.`, and an optional `%zone` of `[A-Za-z0-9._-]`). Anything else is refused with a sentence naming the character: whitespace, quotes, shell metacharacters, control and invisible characters, bidi overrides, look-alike dashes. `user@domain@host` is refused too; such a login goes in a `~/.ssh/config` alias with `User`. Two host strings are the same place when their user parts are equal and their host parts equal ignoring case.
- **Launch:** `ssh -T -o BatchMode=yes -o ConnectTimeout=10 -o ServerAliveInterval=15 -o ServerAliveCountMax=3 -o ClearAllForwardings=yes -o ControlMaster=no -o LogLevel=INFO -- <host> sh -s`. No password or passphrase prompt can appear; a host that needs one fails with `ssh`'s message, which the location shows. The keep-alives stop a host that goes to sleep mid-pass from hanging the sync.
- **How a failure is read:** `ssh` exiting with its own error is unreachable when it couldn't resolve, reach or stay connected to the host, or gave up without a word (not an error, §5), refused when sign-in was refused, and a host-key failure when the key changed or isn't known yet (told apart, each with its own advice), which is shown plainly and never bypassed. Any other failure carries the tool's last line as its reason.
- **Adding** runs the connection test: connect, find the tools, then ask each provider what it finds there (which agents are present, and how many sessions). A host that fails the test can still be added, so a machine that is asleep can be set up now and synced when it wakes.
- Windows ships an OpenSSH client; if `ssh` isn't on `PATH`, adding an SSH location says so.
- **Which machine a host is,** for a copy whose app recorded the host it ran on (§7.7): `ssh -G -- <host>`, run on this machine with the owner's own config, through the same `ssh` the launch runs (on Windows, OpenSSH's `ssh.exe` from `PATH`). It prints the settings a connection would use, after `Host` and `Match` blocks, `Include`s and the defaults. It opens no SSH connection and never runs a `ProxyCommand`, but it is not inert: it runs the owner's `Match exec` commands (with `%h` the host), and with `CanonicalizeHostname` set it looks names up in DNS. So it is asked as little as can be: each host string's answer is kept for the app's life, until `~/.ssh/config` changes or a day has passed; only the hosts of copies shown alone are asked, and a location's host only when one of those resolved and has to be compared with it; at most four at once, in a job of its own after a pass, so that no location shows syncing meanwhile. Only `hostname`, `user`, `port`, `proxyjump` and `proxycommand` are read, their keys in any case (`none` is none); the rest is ignored. A host `host_problem` refuses is never handed to it and is no machine. An answer without the first three is no machine; a run that can't start, fails or takes more than five seconds is no answer, and keeps what was said of that host before (it is logged once a run of the app). It is a launcher like any other: refused once launchers are (§12), and behind a seam (`transport::ResolveHost`) that tests and scripted runs answer with a stand-in. Two host strings are the same machine when both resolve and their host names (ignoring case), users, ports and the way there (`ProxyJump`, and `ProxyCommand` as its text) are equal: one address behind two jump hosts is two machines. Where `ssh` gives no match, a location whose host is the very same string (`same_place`) is the copy's; `same_place` stays the string rule for adding a location, which runs nothing.

## 7. Providers and the transcript model

### 7.1 The `Provider` trait

Everything specific to an agent is behind this trait (D8). The archive, the sync engine, filing, search and the reader are written against items, sessions and the transcript model (§7.4), and never name an agent.

| On | Method | Purpose |
|---|---|---|
| `Provider` | `id()` | The agent's id: lower-case, stable, used in the archive's paths |
| `Provider` | `detect(transport, scratch)` | Whether the agent is present at a location; if so, a `Source` for this pass. `scratch` is a folder in the archive's `tmp/` for anything the source needs to keep during the pass |
| `Source` | `scan()` | The agent's items there: key, kind, session, length and stamp (§5) |
| `Source` | `hash_prefixes(requests)` | SHA-256 of the first *n* bytes of each requested item |
| `Source` | `fetch(requests, sink)` | The requested byte ranges of items, streamed |
| `Source` | `retention_days()` | How long the agent keeps transcripts there, if it says |
| `Provider` | `parse(session items)` | The transcript model (§7.4) of a session's own conversation, from its archived items |
| `Provider` | `subagent(session items, item)` | One subagent's conversation, read when asked for |
| `Provider` | `classify(key)` | The kind of an item and the session it belongs to, from its key alone |
| `Provider` | `copy_of(session)` | Whether a session is a copy another app keeps of one that ran elsewhere, and its words, from its id alone (§7.7) |
| `Provider` | `copy_records(register items)` | What the records an app keeps about its sessions (the location's items of kind register) say of where each conversation ran: the host over SSH and the transcript's path there, as recorded, and the key the provider makes of that path (§7.7) |
| `Provider` | `conversation_of(transcript key)` | The agent's id for a session's conversation from its own transcript's key, for a session its parser can't read (§4.5) |
| `Provider` | `parser_version()` | Bumped when parsing or classifying changes; drives re-indexing (§7.5) |

- **A `Provider` is what is known about an agent; a `Source` is that agent at one location for one pass.** The source holds what `detect` found (the root) and any scratch state (a database snapshot, §7.2), and is dropped when the pass ends. Only a source touches a location. `parse` and `subagent` read from the archive, and never fail: what can't be read is recorded in the transcript. The index (§7.5) and the tool kinds (§7.4) are derived from the parsed transcript, not asked of the provider.
- **An item** is whatever unit the provider archives: a byte stream with a key the provider chooses, stable across passes. The engine versions it (§4.2) without knowing what it is.
- **Tool results carry what the reader needs without knowing the agent:** whether a read's output is numbered and with which separator (`ToolResult::numbered`), a read's file length (`Brief::Lines`), where an edit's change starts (`Brief::Changed`), a content search's mode. Numbers from a transcript are combined with saturating arithmetic.
- **Subagents** are read through `Provider::outlines` (what each says it is and which subagents its calls started, without reading conversations; it must agree with reading them whole) and placed by one rule in `sb_core::transcript::place`: the session's own calls claim first, then each unattached subagent in turn; the first claim places a subagent; a claim on itself or one it is under is ignored. A subagent kept inside the session's own transcript is named by the provider (`<transcript key>#<byte offset of its first record>` for the first provider); the reader treats names as opaque. `Stored::load_head` reads the head of a stored body without the rest.
- **Providers are registered in one list** in `sb_core::provider`. Every location is asked by every provider; each pair where `detect` finds the agent syncs.

### 7.2 Two shapes of source

Agents store transcripts differently, so fetching is the provider's job, with a shared helper for each common shape.

- **A file tree** (Claude Code; any agent that writes files per session). The `FileTree` helper implements `scan`, `hash_prefixes` and `fetch` from a root and a function that classifies a relative path. Items are files, keys are relative paths, and the stamp is size and modification time. A provider for such an agent is three things: where the root is, how paths map to sessions, and a parser.
- **A database** (an agent that keeps its sessions in SQLite). The `DbSnapshot` helper reads the database file with its write-ahead log and rollback journal through the transport into a scratch copy in the archive's `tmp/`, has the location hash the journals, the database and the journals again in one request, and keeps the copy only if every hash and length matches and nothing grew (copying again otherwise, and giving up after a few attempts on a database that never stops committing), and opens the copy with writes refused (SQLite itself may still roll a hot journal back in the copy). SQLite never opens the database at the location. The provider then defines its items as **exports**: per session, a lossless, deterministic byte stream of that session's rows, one record per line in the order they were inserted.
  - Because records come out in insertion order, a session that gained messages is an append and extends its version; a row edited or deleted changes earlier bytes and starts a new version. §4.2 applies unchanged.
  - The scratch copy is deleted when the pass ends. Only the exports are archived.
  - The export format has a version, recorded with each archived version. Changing it re-exports into new versions; formats are never mixed within one.
  - Nothing is written at the location, and the agent's own tools are not run there (FEATURES principle 4).
- **Neither.** A provider can implement the four methods itself.

Which shape another agent has (opencode is believed to use SQLite; pi is unchecked) is established when its provider is written. Nothing here assumes it.

### 7.3 Claude Code

Observed with Claude Code 2.1.325 on macOS, 2026-11-15, from the structure of real transcripts (file names, record types and key names; no content). Transcript files run from a couple of megabytes to tens of megabytes; the largest seen run past 100 MB. The layout inside WSL was checked in phase 1 and has the same shape.

- **Shape:** a file tree (§7.2).
- **Root:** `$CLAUDE_CONFIG_DIR` if set, else `~/.claude`; transcripts are under `projects/`.
- **Layout under `projects/<project>/`**, where `<project>` is the starting directory with its punctuation replaced by `-` (seen for `/`, `.`, `_` and spaces), so the name can't be turned back into the path:

| Path | What it is |
|---|---|
| `<session>.jsonl` | A session's main transcript |
| `<session>/subagents/agent-<id>.jsonl` | A subagent's transcript |
| `<session>/subagents/agent-<id>.meta.json` | The subagent's type, description, and the `toolUseId` of the call that started it |
| `<session>/subagents/agent-<id>.prefix.json` | Bookkeeping beside a subagent (also beside workflow agents) |
| `<session>/subagents/workflows/<wf>/agent-<id>.jsonl` (+ `.meta.json`, `journal.jsonl`) | Subagents run by a workflow |
| `<session>/tool-results/<name>.{txt,json,png,jpg,html}` | Tool output saved outside the transcript; the folder is flat |
| `<session>/custom-title.json` | The session's title, when one was set |
| `<session>/workflows/…` | Workflow definitions and scripts |
| `memory/<name>.md` | The project's memory files (archived; not shown in v1) |
| `<session>.<name>.json`, `sessions-index.json`, other files | Sidecars beside a transcript, and project-level files that belong to no session |

- **The tree is irregular, and all of it is archived.** Seen on macOS and inside WSL across many releases: a session folder with no main transcript (most still hold subagent transcripts), a transcript with no folder, stray `.txt` files in a session folder, empty files and empty `memory/` folders. A file the provider doesn't recognise is still an item. A project-level file belongs to a session only when its name starts with a session id, which is UUID-shaped; otherwise it is a project item with no session.
- **Names are tame:** project folder names start with `-`, use letters, digits and `-`; no links or special files were seen, and no two keys that differ only in case.
- **A transcript is JSON Lines.** Each record has a `type`. Over twenty types are seen; the conversation is in `user`, `assistant`, `system` and `attachment`, and the rest is bookkeeping (`api-request` and its relatives, which are about a quarter of a transcript's bytes, `queue-operation`, `last-prompt`, `custom-title`, `file-history-snapshot`, and others). The set changes between releases. The parser lists the types and the `attachment` and `system` kinds it knows carry no conversation; anything not listed is kept and shown as unrecognised, never dropped silently (D5).
- **Conversation records** carry `uuid`, `parentUuid`, `timestamp`, `sessionId`, `cwd`, `gitBranch`, `version`, `entrypoint` and `isSidechain`. `assistant` records add the model and usage. Content is a list of blocks: `text`, `thinking`, `tool_use` (assistant) and `tool_result` (user), paired by the tool-use id.
- **A reply is split across records:** mostly one `assistant` record per content block, all sharing `message.id` and repeating the same `usage`, so tokens are counted once per message id. Records are also written again under a `uuid` already used.
- **Records form a tree** through `parentUuid`, and it forks without any rewind: calls made at once chain their `tool_use` records and each result hangs off its own call, so walking up from the latest record would drop results. Parents are resolved after the whole file is read. Everything is shown except a side branch whose first words are the user's prompt, which is what a rewound conversation leaves; those are kept and not shown in v1. No rewound conversation has been observed yet, so that shape is assumed.
- **Much text in the user's role is not the user's.** Markers are `isMeta`, `origin.kind` and wrapper elements (reminders, command output, task notifications). Leading wrappers are peeled off as notes and the rest is judged on its own. A message from another session is a prompt with its sender; a prompt delivered mid-turn exists only as an `attachment` of kind `queued_command`; an interruption is a note. A subfolder's `CLAUDE.md`, read as the agent starts working in that subfolder, is an `attachment` of kind `nested_memory` (its `displayPath`, and its text with `contentDiffersFromDisk`): a file loaded into the context (§7.4). Many sessions have no prompt typed by a person at all.
- **Compaction:** a `system` record of subtype `compact_boundary` with no parent, a `logicalParentUuid` and the token counts before and after; its summary is a `user` record marked `isCompactSummary`.
- **Saved output:** a result too large for the transcript is a note in the transcript carrying the path of a file under `tool-results/`; the file's name is not the tool-use id. Images are inline base64, and image files under `tool-results/` duplicate them.
- **Subagents** are linked to the call that started them by the `agentId` (or, for a workflow, the `runId`) in the call's result, with the `toolUseId` in `.meta.json` as the fallback. A subagent can start subagents. A few link to nothing and are kept as unattached.
- **A session's key is its project folder and its id.** The same id can appear under two project folders; those are two sessions.
- **The desktop app's copies of sessions it ran over SSH.** When the Claude desktop app runs Claude Code over SSH (into a WSL distro or a Mac), Claude Code writes the transcript on that machine as usual, and the desktop app keeps a copy on the machine it runs on, under its own `projects/ssh-<id>/`: one folder per session, holding `<session>.jsonl` under the original's session id, and that session's subagent transcripts loose beside it (`agent-<id>.jsonl`, not under `<session>/subagents/`). Its records are the original's, with `entrypoint` `claude-desktop`; most copies are the original byte for byte, some a few records behind it. The provider makes the folder the session (`ssh-<id>`), so the loose subagents are its own and are linked to their calls by `agentId` as usual, and says the session is a copy from its id (`copy_of`, §7.7): "Claude Desktop's copy", which ran over SSH on a machine it doesn't name. The transcript doesn't name the host: on the owner's PC no record field is in a copy that isn't in its original. The desktop app does, in a JSON file per session that it keeps in its own data folder, outside the agent's root: `claude-code-sessions/` under `%APPDATA%\Claude` on Windows and under `~/Library/Application Support/Claude` on macOS. As observed on the owner's PC, the records are two folders down, `claude-code-sessions/<a>/<b>/<name>.json`, every session's together in the inner folder (seemingly an account's and an organisation's folders); a record one folder down, `claude-code-sessions/<a>/<name>.json`, is taken too. The folders' names are not ids of sessions and are not read. Seen on the owner's PC, by field name only: `cliSessionId` in nearly all, with `priorCliSessionIds`, `priorRemoteCliSessionIds` and `lastAssistantCliSessionId`; `sshConfig` in most, with `sshHost` (the host as the app hands it to `ssh`) and sometimes `id`, `name` and `source`; `sshRemoteTranscriptPath`, the transcript's path on that machine; rarely `wslConfig`; and `cwd`, `originCwd`, `sessionId`, `startedFromEnvironmentId`, `envScopeId` and `subagentsTruncatedFor`. On macOS, a session run there holds no host. The provider archives the `.json` files one or two folders down there (`claude-code-sessions/<a>/<name>.json` and `claude-code-sessions/<a>/<b>/<name>.json`), at whichever location has the folder (under `$APPDATA` when that is set, else under the home's `Library/Application Support`), as items of no session of kind register, keyed by their path relative to the app's data folder (no key under the agent's root starts so), and reads them for where each copy ran (`copy_records`, §7.7). Nothing else in the folder is archived (a file at its top, one deeper, or one that isn't `.json`): what else the app keeps there is unknown, and not the owner's transcripts. Which session a record is of comes from its fields alone (below). These files are the desktop app's own state, not a documented format: one that isn't JSON, a field missing or of another type, says nothing, and nothing about them fails a sync. A conversation is joined to the files that name it by precedence, the first that has any taken alone: its own record (`cliSessionId` is its id), which wins outright; else a record whose `sshRemoteTranscriptPath` is its transcript (`<id>.jsonl`); else records that name it among the session's earlier or last ids (`priorCliSessionIds`, `priorRemoteCliSessionIds`, `lastAssistantCliSessionId`), and only at this level do records that say different things of it (another host, another path) leave that thing unsaid. Another session's record is never taken when the conversation has its own: a session resumed or forked names its predecessors, and on the owner's PC most copies' ids are in more than one record. Ids held elsewhere in a record (`publishedArtifacts`, `subagentsTruncatedFor`) are mentions, not identity, and are never read. A path is said only of the id it names. `wslConfig` is not read: its shape has not been seen, and which distro a session ran in can't be taken from it unambiguously until it has. One session per folder is as observed on the owner's PC (none was seen with more than one transcript); should a folder hold more, only its first transcript is read, as of any session, and it is not deleted for good (§4.5). On the owner's PC most copies matched an original byte for byte, the rest were behind it, none was seen ahead; nearly all loose subagents attached, and those that didn't are the copies' own, unattached (§7.7).
- **Older releases wrote subagents inline:** records marked `isSidechain` inside the main transcript, with their own parent chain. They are gathered into a subagent conversation, attached to the call whose prompt matches when exactly one does, and never shown as the owner's turns. This shape is from memory of older releases and is unverified until the check runs over an older archive.
- **Shell mode:** a command the owner ran with `!` is a prompt whose text is the command; its output is a note.
- **Project path** (D9): the first `cwd` in the main transcript. It matched the directory name's encoding in every session sampled; a minority touched more than one directory later.
- **Title:** the last `custom-title` record, else `custom-title.json`; else the start of the first prompt.
- **Retention:** `cleanupPeriodDays` in `settings.json`, 30 days when absent and at least 1 (confirmed against Claude Code's documentation). The same cutoff removes a session's `subagents/` and `tool-results/`. Sessions started from the desktop app have their own setting, `desktopSessionCleanupPeriodDays`. The provider reads the user-level `settings.json` at the agent's root only; a project or managed override is not seen. When the sweep runs, and whether age is by modification time, is not documented.

### 7.4 The transcript model

Provider-neutral, what the reader renders:

- **Transcript:** session facts (the agent, title, project path, branch, entrypoint, and the agent's id for the conversation, §7.7; whether the session is a copy kept elsewhere is said by the provider from its id, `copy_of`, not parsed), the session's own conversation, and any subagents no call is known to have started. A session whose main transcript is missing still has a transcript: no conversation, and its subagents unattached.
- **Conversation:** blocks in recorded order with their parent links, and the turns that are shown. A turn is a prompt and everything up to the next one; a conversation's first turn may have no prompt. A conversation says how it ended: whole, inside a record (a version can end mid-line, §4.2), or unreadable from some point (§4.4), keeping what was read.
- **Block:** a prompt (text, images, and its sender when it isn't the owner), a reply, thinking (text and duration), a tool call, a compaction boundary, a note (text the agent's harness wrote, by kind), a file the agent loaded into its context partway through (its path as the agent showed it, its text, and whether that differs from the file on disk; Claude Code's nested memory files), or an unrecognised record kept raw.
- **Tool call:** the agent's tool name, its kind, a typed input where the input fits the kind and the raw input always, the result, and its subagents. A result has a status, a time, its output parts (text or image) and a **brief**: what a collapsed row shows without loading output (exit status, lines, lines changed, matches, a subagent's run), captured at parse time where the source says.
- **Large bodies are references, not text.** Tool input and output, file bodies, subagent prompts, summaries, the text of files loaded into the context and images are an item, an offset and a length, loaded when a row is expanded. Prompts, replies, thinking and notes are in memory.
- **Subagents are read on demand.** Parsing a session reads its main transcript only (tens of milliseconds for the largest seen); a subagent's conversation is read when its call is expanded, and the index reads them all.
- **Conversations are made through one builder** that holds the model's rules (turn splitting, parent before child), so every provider's output obeys them.
- **Tool kinds are common to all agents:** shell, read, edit, write, content search, file search, todo list, subagent, web search, web fetch, MCP, other. Each provider maps its agent's tool names onto them (Claude Code: Bash, Read, Edit, Write, Grep, Glob, TodoWrite, Agent, WebSearch, WebFetch, and `mcp__…` tools; the three in the middle are absent from current releases). The kind comes from the tool's name and is on the call. The reader has one renderer and one icon per kind (DESIGN §4.2.4) and shows the tool under the agent's own name; a tool a provider doesn't map renders as `other`, with its name, input and output.

### 7.5 Indexing and large files

- Parsing streams a transcript line by line and never holds the file in memory; the model holds a few percent of the bytes parsed.
- **An index parses several sessions at once:** one fewer than the processors there are, at most four, since it is background work beside the app and whatever else the owner runs. That is the most parsed at once over every index the app runs: the parsing threads of all of them share as many permits, and an index's own thread, which commits, never waits for one. Parsing threads have a set stack (8 MB) on every platform; an index that can't start one parses on fewer, or on its own thread. Rows are committed one session at a time on one thread, in the order the sessions are taken in, and each parse yields the session's row and its search text both (§10), so a session is read once by an index.
- **What an index holds:** at most twice as many sessions as threads are parsed and not yet committed; a parse keeps only what the row and the text are made of, and of each span of text only the first 64 KB, which is all search keeps (§10). So an index holds as many transcript models as it has threads while they parse, those sessions' rows and text, and three batches of text at most, each up to 64 sessions or 4 MB: the one being filled, one handed over, and the one being written. The first step writes its text on a thread of its own, so rows are committed, and the bar moves, while a batch is written; only text that falls two batches behind makes the rows wait. A cancel begins no more sessions; what was parsed and not committed is dropped, to be parsed by the next index, and the text of the rows it committed is written.
- **A session another index has made since is not parsed again.** An index finds what is stale when it starts; a pass beside a start's index can make again a session that grew meanwhile. Before it parses a session, an index reads what its row is made of: when that is its items as they are, by this parser and index, the session is passed over. Two indexes that take the same session at the same moment both parse it, as nothing locks a session: rare, and cheaper than a lock every parse would wait on.
- **The index is one agent-neutral function over a parsed transcript:** title, first prompt, project path, branch, entrypoint, start and end, models, the session's own totals and the totals with its subagents, and the search spans (prompts, replies, tool commands and paths, each with the block it opens at; a subagent's text opens at the call that started it).
- **Staleness is a fingerprint** over each of the session's items (its kind, the version read and the newest version, with their lengths, and whether the version read is damaged), stored with the row beside the parser's and the index's versions. A pass indexes sessions whose fingerprint moved; a version bump is worked off in the background, never-indexed sessions first, then newest first. A read error from the operating system is not recorded as the session's state: the row keeps what it had and is tried again.
- **The backlog is one index's at a time:** rows another version of the parser or of the index made, and text not yet of its rows (the search database made anew, text an index could not write). The index of every location, which a start runs, takes it, waiting for leave if an index of one location has it; an index of one location takes it only when no other index has it, and otherwise indexes what changed, as a pass's does. A pass's index makes the rows of what the pass changed and their text, never the backlog: passes run beside a start's index, and two indexes working the same backlog parse the same sessions newest first at the same time, one throwing its work away. The app, not the pass, starts the index of every location when a pass's index, or an index of one location, says it left a backlog and none is running, so none is ever left. A pass says so only for text an index could make: not when search is not to be had, not for a row the archive could not be read for (a start's index reads it again), and not for an agent it doesn't hold; else every pass would start an index for nothing. The index of every location says, while it waits for the backlog, that it waits (DESIGN §4.1).
- **A provider can reclassify archived items** (`classify(key)`): when its parser version changes, the engine re-applies it to every archived item, including those gone at the source, so a fix to how files map to sessions reaches the whole archive. The owner's state follows the session's own transcript: when one session becomes two it goes with the first own transcript; when two become one the first to arrive keeps its state; state left under an id that no item has is removed. A pass and the background index change an item's session through the same code, so neither can strand state.
- A session is always parsed from its start. That is fast enough that the reader needs no per-turn byte offsets; search results name a turn and a block.
- Parser output is cached in memory per open session only; nothing parsed is written to the archive except the derived tables.
- The index rows carry the parser's version and the index's. A new version of either re-indexes in the background, newest sessions first.

### 7.6 Adding an agent

1. A module under `provider/` that implements the trait, on `FileTree` or `DbSnapshot` where one fits.
2. One line in the provider list.
3. Its tool names mapped to the common kinds.
4. A display name, a mark and the mark's colour for the UI (the theme holds no agent's colour).
5. A fixture builder for its storage in `sb_test_support`, and golden parser tests.

Nothing else changes: no migration, and no change to the archive, sync, filing, search or the reader. If adding an agent needs one, the seam is wrong and is fixed first.

### 7.7 Copies of a session kept elsewhere

An agent's app can keep its own copy of a session that ran on another machine (§7.3: the Claude desktop app's copies of sessions it ran over SSH). Both are archived, since a copy may outlive its original, and the library shows the conversation once. The provider says what a copy is; the catalogue and the library match and choose without knowing any agent.

- **What the provider says:** `Facts.conversation` (§7.4), the agent's own id for the conversation, which every copy of it shares (Claude Code: the session id that names the transcript); and `Provider::copy_of(session)`, said from the session's id alone, as `classify` is: whether it is a copy, and the words it is shown with (a label, "Claude Desktop's copy", and where it ran as far as the copy says). Being a copy doesn't depend on a parse, so a copy its parser stops on is still one. Only the provider knows where copies are kept and what they look like.
- **Matching:** a copy and an original are the same conversation when they have the same provider and the same `conversation`, and either the same project path as recorded (the first `cwd`, D9), or the copy's record names the original's transcript: the original's main transcript is at a WSL or SSH location, its key is the one the provider makes of the path the app recorded for the transcript where it ran (`copy_record.key`; Claude Code: from the path's last `projects/` on, when that is a session's own transcript), and that path lies under the root its provider last reported there. Not by the id alone: Claude Code gives one id to two transcripts under two project folders of one machine (§7.3), which are two sessions, and a copy's records are its original's, so its first `cwd` is the original's. Two unrelated sessions would have to draw the same random id and start in the same directory to be merged. The path is the second key, for a copy whose first `cwd` is missing or not its original's; it loosens nothing that could merge two sessions, since the id must still be the same and a path names one file on one machine. A path the app wrote in another form (with `~`, say) is under no root and matches nothing; `check` counts how the recorded paths are written. A session with no `conversation` (no main transcript) matches nothing. A tombstone (§4.5) keeps the first key alone; a copy matched by its path is deleted for good with its original, as one of its conversation.
- **What is shown:** of the sessions of one conversation, every original is shown; a copy is shown only while none is archived, and of several such copies the one the owner filed by hand, starred or put in Trash, then the one archived first (by its transcript's item), then by identity: a choice that doesn't change as copies grow or are synced. The rest are hidden from every page (Trash included), count (Settings' totals too), search result, filter, the paths editor's previews and the palette's recent sessions. This is a condition of the library's queries on the derived rows (`catalogue::session::SHOWN`), not stored, so it follows the archive with nothing to keep in step: an original that arrives later replaces its copy at once, with no duplicate.
- **Where a lone copy is from:** never from the location that kept it. The library attributes a session to a location (`Session::ran_at`): an original to its own, a copy to the location it ran at when that is known (below), and otherwise to none. A copy attributed to none carries its copy tag wherever a location would show, the Location filter and `from:` never match it, Unsorted groups it by path alone, the paths editor offers its path for any location, filing applies only paths attached for any location (§8), and per-location counts leave it out.
- **Where a lone copy ran.** An app that keeps copies may keep records of its sessions beside them, as the Claude desktop app does (§7.3). The provider reads them (`Provider::copy_records`, from the location's items of kind register) for what each says of a conversation: the host it ran on over SSH, as the app recorded it, the path its transcript had there, and the key the provider makes of that path. The catalogue keeps that per location, provider and conversation (`copy_record`), derived from the archive and made again from the register items at every index over them (each pass, and a start's index), so a reindex makes it again and a record the app has since deleted still counts. **The records are archived** because scrollback archives what it reads, they are small, the app deletes a session's record with the session while the copy is kept (so an attribution taken at a scan would have nothing to be made again from), and their format is not documented, so a later parser that reads more of it (a WSL distro, say) can make the attribution again from what was kept. They hold the owner's host names, in the owner's own archive. A host means something only to the `ssh` of the machine that ran the session, the one whose app kept the copy, so only records kept at This PC's location are resolved, through this machine's own config (§6.4):
  - The recorded host of each copy shown alone, and the host of each SSH location not removed, are resolved with `ssh -G` (§6.4) and compared by what they end at (host name ignoring case, user, port, and the way there), never as strings: the app may hold `user@host` where the location was added as an alias, or the reverse, or another user, port or jump host. A hidden copy's host is not asked: nothing shows where it ran.
  - **Matched:** the copy is attributed to that location. It carries the location's tag (cards, rows, Trash, search results, the facts' From), the Location filter and `from:` match it, Unsorted groups it with that location's sessions of its path, filing applies the paths attached for that location (§8), and the location's filter and tag include it. Its holdings (what the locations sheet says a location holds) don't: they are what was archived from there, and the copy was archived from This PC. Of two locations that resolve alike, the one added first wins. A removed location is no target: a copy whose host is only a removed location's is shown with the host, as one that is no location.
  - **Resolved, and no location:** the copy tag shows the host as recorded in place of the provider's label, and the facts say "Ran over SSH on <host>"; it is still from no location.
  - **Not resolved** (no record, a record without a host, `ssh -G` missing, failing or slow, or an answer without the three settings): the provider's words, as before.
  - **Localhost is WSL, not SSH.** A host `ssh -G` resolves to a loopback address (`127.0.0.0/8`, `::1`, `localhost`) is this machine's own sshd: the desktop app's "SSH into WSL" reaches a WSL distro so. Such a copy is never matched to an SSH location. It is the WSL location's when there is exactly one; of several, the one whose home holds the `cwd` the record says the session started in (the home its provider's root there says, `Provider::home_of`; Claude Code: the folder above `~/.claude`); of none, or several that hold it, none. With no WSL location it stays the app's copy with no host shown: "localhost" says nothing to the owner. Which distro is decided when the records are read (`copy_record.wsl`), so a distro added later is weighed at This PC's next pass.
  - **When:** `sync::attribute` runs as a job of its own after every sync of any location and after a start's index, one at a time; it is stopped with the indexes when the app leaves the archive, before it writes. It writes what it found to `copy_record` and refiles the copies whose location moved, in one transaction, and a change refreshes the library. Records made again by an index refile too, when a copy's location goes with them. `ssh` that can't be asked keeps each attribution as it was: a sync on a machine without `ssh` moves nothing. An original that arrives later takes over as for any copy; the attribution only says where a lone copy is from. Copies kept at another location (an SSH host whose own desktop app keeps copies) have their records archived but are not resolved, since this machine's config doesn't speak for that one's.
  - **The records are read only when they change:** an index reads a location's register items again only when they or the parser are not what they were last read whole from. One that can't be read is left out and the rest are taken; what it said before stays until it is read. Nothing about the desktop app's folder fails the agent's own pass: it is looked for apart, what can't be listed in it is logged rather than counted against the pass, and a folder that can't be listed is as none.
  - **A copy newly matched by its path** (a record written after its copy was shown alone) hides it behind its original, as any match does, and what the owner set on it while it was shown alone moves to the original only by the takeover's rules (`as_copy`); state set before 0.1.1 is not `as_copy`, so an upgrade can leave state on a copy that is now hidden.
- **A copy longer than its original** has bytes the original lacks, usually because the original's location hasn't synced since. The original is still the one shown: it is the session of the machine it ran on, its versions and history are there, and its next sync usually catches up; a copy standing in would move the session between locations, filters and folder rules from one sync to the next. The reader's facts say how each copy compares with the session read: the same, behind (its start, and no more), ahead (all of it, and more), or different (neither holds the other). The versions read are compared by length and hash, and where the lengths differ, the longer's start is hashed as far as the shorter goes (one read of the longer, off the UI thread, only for a session with copies). Where a copy is ahead or differs, it is flagged and **Read the copy** opens it (DESIGN §4.2.8). A copy opened so stands for its original: it says whose copy it is and links back, Back returns to the original, J and K go on from the original's place, and Star acts on the original (the reader offers no Trash or Move; the page's do, on the page's sessions).
- **The owner's state** (star, Trash, folder) belongs to the session shown. A hidden copy's state shows nowhere. What the owner decides of a copy while it is shown alone is marked so (`session_state.as_copy`); when an original's row is first made, it takes over that state of the copy that was shown in its place until then, if it has none of its own, and the copy keeps none of it, so nothing moves twice. A row made again (an upgrade's re-index, a rebuilt index) takes over nothing, and neither does what was decided of a session before it was known to be a copy: a duplicate the owner trashed in 0.1.0 leaves its original alone. Delete for good takes the whole conversation (§4.5).
- **Catalogue:** the `session` row gains `conversation` and the copy's two texts, indexed by provider and conversation; `session_state` gains `as_copy`; `tombstone` gains the conversation and the copy's label. One SQL fragment says what two sessions of one conversation are, for every query that matches them. A later step adds `copy_record` (where a copy ran, above), which the library's attribution (`RAN_AT`) and the matching's second key read; `item.kind` takes `register`. The index version goes up so every row is made again, and the provider's parser version so that classification reaches archived copies.
- **Loose subagents past a copy's end.** A copy behind its original can hold the transcript of a subagent its original started after the point the copy stops: no call of the copy's started it, so it is the copy's, unattached, read on its own (the reader shows those after the conversation). On real data most loose subagents attach; `check` says how the copies of those left unattached compare.
- **Checking it against real folders:** `cargo run --release -p sb_core --example check -- <home> --with <home>` prints, beside its other counts, the copies found under the first home, how many match an original in either home and whether each is the same, behind, ahead or different, the copies with no original, the loose subagents attached, and the record fields seen in copies but in none of their originals. It also counts the likely misses of the matching: copies with no original of their path but one of their id with another, and copies with no project path. Beside the home folders it reads the desktop app's records under the first home (under `--appdata <folder>`, which stands for `%APPDATA%`, else `AppData/Roaming`, or under `Library/Application Support`) and counts: the copies with a record, with a host, those whose host `ssh -G` resolves on this machine (it opens no SSH connection, but runs the owner's `Match exec` commands and may look names up in DNS with `CanonicalizeHostname` set), those matched to an SSH host given with `--location <host>` (any number of them), and the rest unresolved; how the recorded transcript paths are written, how many the provider makes a key of, and how many of those are their original's; which of a record's text fields hold a copy folder's id (field names printed only as far as they are identifiers); the copies whose record has `subagentsTruncatedFor` beside those with loose subagents left unattached; the copies joined by each rule of the join, and those with more than one record by `cliSessionId`; and the hosts and copies that resolve to loopback, with those a WSL distro would take given its home with `--wsl-home`. For each copy with an original, it reads the subagents of both and counts those attached in both, only in the original (by how the original attached them: its call's `agentId`, a workflow's run, or a `.meta.json`), only in the copy, and in neither. Counts only, as everything `check` prints. Against an archive, `cargo run --release -p sb_core --example sync -- <archive folder> copies` counts what the library shows: the sessions shown, the copies shown alone, and the copies hidden behind their originals by how each compares.

## 8. Filing

- **Normalising a path** for comparison: split into components; on Windows-style paths (`X:\…`) fold case and accept either separator; map a WSL mount path to its drive form (§6.3); drop a trailing separator. A share path (`\\server\share\…`) is its own root, and one that names a WSL distro keeps its case. A path with no components (empty, `.`, `/`) can't be attached. The path as typed is kept for display.
- **A session's candidates** are the attached paths whose components are a prefix of the session's project path, and whose location is unset or is the session's. A copy shown in place of its original (§7.7) has no location for filing: only paths attached for any location claim it, never one attached for the location that kept it. Its path is read with no location's drive mount.
- **The longest candidate wins,** and of two equal ones the path attached for the session's location beats the same path attached for all. Its folder gets the session, marked as filed by rule.
- **The same path can't be attached to two folders** for the same location scope; the second attach is refused and names the first folder. On one folder, the same path may be attached for two different locations (the same project on two machines), but not where the scopes overlap: the same location twice, or any location beside a single one. Spellings that normalise alike are the same path, and a WSL mount path is its drive form everywhere (`/mnt/d/Projects/app` is `D:\Projects\app`); a WSL location whose distro mounts drives elsewhere supplies its own mount (§6.3). A typed path is trimmed and must be absolute.
- **When rules run:** whenever a session that isn't filed by hand is indexed; and when a folder's paths change or a folder is deleted, over every session not filed by hand. So such a session is always where the rules put it. A session filed by hand is never moved by a rule. A session whose parse failed stays where it is.
- **Sessions in Trash** are left out of filing; restoring one files it again, by hand where it was filed by hand and its folder still exists, otherwise by the rules.
- **Folder names** are unique among siblings, ignoring case. Creating takes the next free name ("New folder 2", "app 2" for Create folder from a path); renaming or moving onto a taken name is refused; deleting a folder renames any child that would clash with its new siblings. A catalogue that already holds clashing siblings opens as it is.
- **Changes to many sessions** (filing, handing back, Trash, restore, star) are one transaction each, and report what they changed, so Undo puts back exactly what that transaction saw.
- **File automatically** hands a hand-filed session back to the rules: it clears the mark and runs filing on that session.
- **A folder contains its subfolders' sessions.** Its page lists them and its count includes them.
- **Deleting a folder** drops its paths, moves its subfolders up to its parent, and hands its sessions back to the rules, hand-filed ones included: each goes to the folder another attached path claims, or to Unsorted.
- **Unsorted** is every session without a folder, grouped by project path and location: the same path on two machines is two places. Groups merge across locations only where the path has a drive form (a WSL mount path and its Windows path).

## 9. Reader

- **A virtualised list of blocks.** Tool calls render as fixed-height activity rows until expanded, so a session with hundreds of calls has a known height and scrolls without measuring everything.
- **Parsing is off the UI thread.** The session's own conversation is parsed whole (§7.5) and shown; subagents are read when their calls are expanded.
- **Tool output is loaded when its row is expanded,** including output saved in `tool-results/`. A collapsed row's short result comes from the call's brief (§7.4). Segments are capped in size (§4.1), so loading a body near the end of a large transcript decompresses one segment, not the whole version.
- **Markdown** per D11, prepared off the UI thread. A body is cut at blank lines into regions of at most 8 KiB, each parsed on its own, within 100 ms a body; fenced code never goes to the Markdown parser. Each piece is sanitised, then parsed as the view parses it and timed; one whose view parse takes more than 8 ms per 4 KiB is drawn as plain text. Reference definitions are carried to the pieces that use them as the parser read them, written out on one line. The scan that finds fences and counts nesting is a heuristic for quality; the bounds don't depend on it.
- **Code is highlighted** with tree-sitter into token kinds the theme colours, as dv's `syntax` does: always off the UI thread, two jobs at a time with prose, within 50 ms a block (up to 16 KiB, parsed 2 KiB of whole lines at a time, read 256 bytes at a time), cached by the code's text (8 MiB). Past the budget a block stays plain. The reader's highlighter replaces gpui-component's for every `TextView`, so no other highlighter runs. Grammars whose C scanners can abort the process (Bash, Kotlin, YAML) are not built in; shell code (`bash`, `sh`, `shell`, `zsh`, `console`) is coloured by a hand-written linear lexer.
- **Every job over a transcript's content is guarded:** a panic is caught, logged and drawn as plain text or as a part that couldn't be read; it never reaches gpui's executor. A job that lands lays out only its own rows; only opening or closing something lays out the session. Closing a session stops its jobs at their next step.
- **Bodies are read to their head** (about 16 KiB a part) until Show all; images decode within a memory limit, at most two at a time; text drawn outside prose (titles, prompts, paths, models, branches, folder and location names) goes through one cleaner that turns control and direction characters into visible markers and caps combining marks. Copy puts on the clipboard what was shown, markers included, without the zero-width spaces the sanitiser adds.
- **Diffs** for Edit and Write come from the tool call's own input and result. dv's diff rows and highlighting are lifted (D15).
- **Subagents** render through the same block list, nested and collapsed by default, under the call the parser attached them to (§7.3).
- **Find in session** searches the parsed text of the open session, not the archive's index.
- **Opening at a search match** takes a one-shot request (`ReadAt`): the reader expands the call and each subagent on the way to the match, read from the placement's parents (only the ancestors are read), scrolls there and flashes the hit; if the block no longer holds it, the first block that does is used.
- **End** follows the column's end until any other key, a click or the wheel.
- **On macOS** the app allocates with mimalloc and hands memory back after a session closes and after a sync pass, so the resting footprint stays near where it started; Windows gives freed memory back on its own.

## 10. Search

- **The search text lives in its own database,** `search.db` beside the catalogue: a row per indexed span (session, turn and block, kind: title, prompt, reply, command, path; for a subagent's text, the innermost subagent's item and the turn and block inside it) and an FTS5 index over them. It is derived: never backed up, opened only when something needs it, and made again from the archive when it is missing, damaged or out of date; each index's text step opens it first, so a file of an older layout is rebuilt at start. So is one of a newer layout: an older release that opens a search database a newer one migrated (a schema step it doesn't know) throws it away and makes it again from the archive, which costs a full index of the text and loses nothing; unlike the catalogue's, its migrations are never a reason to refuse an archive. If it can't be opened (another program holds it), the archive still opens and search says it is unavailable. The catalogue holds none of it, so the catalogue and its daily backups stay small and hold no transcript text.
- **The index is `trigram`, without positions** (`detail=none`). Measured against `unicode61`: substring matches inside identifiers and paths, and CJK, are the requirement, and only trigrams find them. A term is looked up by its three-character runs and each candidate span is then checked against its text, so results are exact. On a generated corpus of 50,000 sessions the search database is about one and a half times the indexed text; the catalogue beside it stays under 100 MB.
- **Indexed:** titles, user prompts, assistant text, tool calls' commands and paths, up to 64 KiB of any one span. **Not indexed in v1:** tool output and thinking (D10).
- **Subagent transcripts are indexed** under their parent session. A match in one opens the parent at the call that started the subagent, expanded.
- **Matching ignores case, and accents on Latin letters,** exactly as the index's tokenizer folds text (Greek and other scripts fold case only). A session matches when every term appears somewhere in it. The matches shown are the spans holding any term, those holding all of them first. Sessions whose title matches come first, then the most recently active.
- **Short terms.** A query whose terms are all ASCII and shorter than three characters asks for more typing rather than reading everything. A short term in another script (a two-character CJK word) is found by reading the text, which can be cancelled.
- **Filters** are tokens in the query: `in:` (a page: all, starred, unsorted, trash; else a folder's name), `folder:`, `from:` (a location), `agent:`, `model:`, `branch:`, `after:` and `before:` (a year, month or day, in the calendar dates are shown in). A token applies once it is finished (followed by a space); a finished one that names nothing holds the results and says so. Inside quotes `\"` is a quote and `\\` before the closing quote is a backslash; every other backslash is literal, so Windows and UNC paths can be quoted. Trashed sessions are found only with `in:trash`.
- **Indexing is two steps:** session rows first, so a first sync's library appears at once, each with its text made from the same parse and written in batches; then the text the first step could not make (the search database made anew, or text an index could not write), each session parsed again for it. The second step is the backlog's (§7.5): only the index that has the backlog takes it. How many sessions are not yet searchable is a read, and each batch is news an open palette re-searches on. Each step reports how many sessions it has to do (text already of its row is done at once) and how far it is after each one (DESIGN §4.1); the first also says how many rows another version made, which is how a start's index says it runs after an update, and how many sessions' text it has written.
- **The library never waits on search.** A search database that fails while the first step writes text (another program holds it, say) is said in the log and let go of for the rest of the step; the rows go on being made, and the text is the backlog's. Text the first step would write while the index is compacted is left to the backlog at once, not waited with; the backlog's own step, and one session indexed on its own, wait for the compaction instead, in the background, so they never parse for nothing. A row whose text the archive can't be read for when the second step makes it is marked to be read again, by the next index of a start, and is no backlog meanwhile.
- **A row says its text is searchable only when the text is there.** The flag is in the catalogue and the text in its own database, so the two can't be written in one transaction: the flag is set after the text is committed, both under the search database's write lock, which a forget also holds, and text already there is checked under the same lock before a row is said to have it. A crash between the two leaves text without its flag, which the next index finds and flags without parsing; opening the search database also unflags any row whose text is not there, as a backstop.
- **Text taken out of the search index is marked deleted, not taken out securely, and replaced only where it changed.** Taking a span out with FTS5's `secure-delete` costs a search of the index for each of its trigrams, which on a large index is far more than writing it: an index after an update that made every session's text again spent nearly all its time there, minutes per hundred sessions. Marked deleted, a span costs about what writing it does, and FTS5 drops it as it merges the index's parts. The two can't be mixed: taking out securely what an earlier write marked deleted damages the index. So the index never deletes securely, and a delete for good is made good by the scrub (§4.5). A span the session still holds, at the same place with the same text, is left as it is, and a session made again as it was writes nothing. Search keeps finding every session while a new version's index runs, each by its old text until its new text is written, the newest first, and each batch is one transaction. Text an ordinary index replaces stays in the file as marked-deleted entries until the index is compacted: that is acceptable, as the archive still holds that text; text deleted for good is erased at once (§4.5).
- **The search index is compacted when much of it is marked deleted.** What is marked stays until the parts it is in merge, which after a few updates took the file to several times its size. Each transaction that marks spans counts them in the search database, so the count adds up across indexes, cancels and crashes; when it comes to a quarter of the spans there are, the index that has the backlog compacts the index at its end (`rebuild`, as §4.5 does: on a few thousand sessions it took about a second more than merging the index's parts with `optimize`, and left a third of the entries), and says so (DESIGN §4.1). A new version whose parser says the text as before marks nothing, and compacts nothing.
- **A result** carries the session, the turn and the block, so it opens the reader there.
- **Hostile input is text:** at most 16 terms of 256 characters, no query syntax, and every scan checks for cancel.

## 11. UI architecture (`sb_ui`)

- **Services,** as gpui globals or entities, each the only writer of its state: `Archive` (open archive, catalogue reads), `Sync` (passes, location states, progress), `Library` (folders, filing, selection, Trash, deleting for good), `Search` (the palette's queries and recents), `Reader` (open sessions, prose and highlight jobs), `Upkeep` (verify, re-fetch, tombstones), `Settings` (the app's settings file). One `system` module performs reveal, the folder picker, opening a URL and copying; under automation and in tests it records the request instead.
- **Views:** `shell` (title bar, sidebar, main area), `sidebar` (library rows, folder tree with drag and drop, locations), `folder_page` (header, path chips, filters, cards), `reader` (header, block list, facts margin), `locations_sheet`, `first_run`, `search` (the `Ctrl K` palette), `versions` (the history popover), `settings`.
- **Sync runs on background tasks** and reports through the `Sync` service; views observe it. No view starts a process.
- **Drag and drop:** sessions onto folders, folders into folders, a path chip onto a folder. folio's sidebar tree is the precedent, including a pre-rendered drag ghost (GPUI can't rotate a div).
- **Views never name an agent.** A session's agent is shown from the provider's display name and mark (§7.6), beside its model, and agent is a filter wherever model is.
- **Keyboard first,** as the siblings: every action has a key and appears in the palette. The key map is DESIGN's.
- **Automation:** views register targets with `gpui_automation` for the scenarios (§12).

## 12. Testing

- **Fixture trees, never real transcripts.** `sb_test_support` builds a Claude Code `projects/` tree in a temp dir: sessions with chosen sizes, tools, subagents, branches and bookkeeping records. The owner's transcripts are private and never enter the repository or a test.
- **Sync, as unit tests over fixtures:** first sync; append; rewrite; truncate; touch without change; deletion at the source; a file that ends mid-line; a pass cancelled at each step and resumed; a crash between rename and commit.
- **The shell transport, hermetically:** the `Command` launcher runs the same scripts through a local `sh` against a fixture tree, and the whole sync test matrix is run again through it. `SB_TEST_SHELL` names another shell to run it under, `SB_TEST_SHELL_VIA` a container's userland, and `SB_TEST_WSL` a real distro. On Windows these tests run inside WSL, as dv's Linux tests do. GNU and BSD tool variants are both covered (Linux and macOS runs).
- **The provider seam, with a second provider.** A test-only provider in `sb_test_support` keeps its sessions in a SQLite database and uses `DbSnapshot` (§7.2). The same sync tests run against it: first sync, rows appended, a row edited, a session deleted at the source. Search, filing and the reader's model are exercised on its sessions too. It exists so the first real second agent is not the first test of the seam.
- **No launcher in a test or a scripted run.** Distros, hosts and `ssh -G` are answered by stand-ins; `refuse_launchers` makes any real `wsl.exe` or `ssh` (`ssh -G` included) fail and log an error, which fails the scenario.
- **No agent's name outside its provider:** `script/check` fails if `claude` appears in `sb_core` outside `provider/claude_code`, or anywhere in `sb_ui` outside the provider's display name and mark.
- **Filing:** table tests of path normalisation and longest-prefix matching, including the WSL mount mapping and Windows case.
- **Parser:** golden tests from fixture transcripts; a record of an unknown type and a tool of an unknown name must survive.
- **Costs by their growth, not by the clock.** A test that hostile input costs no more than its bytes times the work on two sizes of it and bounds the ratio (`sb_test_support::growth`), so it says the same on a slow or busy CI runner. A latency budget (the view's parse limit, a first paint) is a measurement: `#[ignore]`d, run by hand on a release build; the code that enforces one is tested on times handed to it. A wall-clock bound in the default run is a guard against a hang, or many times what the work takes, with the least of a few tries kept.
- **GUI scenarios** with `gpui_automation_runner`: first run → add a local location → sync → a session appears in Unsorted → create a folder from its path → open the session → expand a tool call.
- **The owner's live checks,** not automated: a real WSL distro on the PC; SSH from the PC to the Mac; a first sync of the real archive, timed.

A release is the owner's: bump `[workspace.package] version`, commit on main and push; `git tag -a v<version>` and push the tag; `release.yml` checks the tag, reuses main's CI for that commit or runs it, builds the packages without caches, and waits for approval of the `release` environment before publishing the files, `SHA256SUMS` and build provenance. A `-rc.N` tag publishes a prerelease that never reaches the feed. Repository settings it relies on: a ruleset so only the owner creates `v*` tags, the `release` environment admitting `v*` tags with the owner as reviewer, immutable releases, Actions limited to SHA-pinned actions, and approval for outside contributors' workflows.

Phase 5 is late only because Local exercises the whole pipeline on the development Mac first. If the owner wants the WSL backup running early, phases 1 and 5 can be done back to back before any UI, with a temporary command-line trigger.

## 14. Risks and open questions

- **Budgets,** to be measured, not yet met by anything: a first sync limited by the transport, not by scrollback (compression and hashing faster than a WSL read); a pass with nothing changed over 20,000 files in under 5 s for Local and under 15 s for WSL; opening a 100 MB session to first paint in under 500 ms; scrolling a 500-call session at the display's refresh rate.
- **Claude Code's format changes between releases.** The provider must tolerate it (D5), and a fixture per observed release guards the parser. The layout in §7.3 is from one machine and one release.
- **The provider seam is proven by a test provider only** until a second real agent exists (D8, §12). The first real one may still show something the trait lacks; §7.6's rule is to fix the seam then, not to work around it.
- **Reading a live database** (§7.2). `DbSnapshot` copies a database that its agent may be writing, without locking it. Re-reading when the files changed and opening the copy read-only should give a consistent snapshot; this is checked against a real agent's database when the first such provider is written, along with how large those databases get.
- **The shell transport across real hosts** (D6): BSD and GNU tool differences, unusual shells, slow links. The connection test is where problems should surface. The fallback is a helper binary behind `Transport`.
- **Provenance when lifting** (D15). Each file lifted from a sibling is checked for where it came from; GPL-derived code is rewritten or replaced, not copied.
- **Index size.** FTS5 with `trigram` over a year of prompts and replies; measured in phase 6 before the tokenizer is fixed (D10).
- **Deleting for good is the one irreversible act** in the app (§4.5). It needs its own tests: nothing outside the session's files is removed, and a location is never touched.
- **A writer that hides its changes.** Change detection is by size and modification time (§4.2). A program that rewrites a file in place and puts its time back, or writes through a memory map, stays invisible: the item reads as unchanged and the archive keeps the older content. Every range that is fetched is proven against the source before it is stored, so this can leave the archive behind but not wrong. A periodic deep check that re-hashes unchanged items is listed for later.
- **`orphans/` is emptied only by a delete for good,** which removes the set-aside copies of the items it deletes (§4.5). Otherwise it only grows: it gains a file when an unrecorded file is in the way of a different segment, or when the owner sets strays aside after a verify. Rebuilding a catalogue from the per-item `source.json` files is listed for later.
- **A database that never stops committing** can't be snapshotted by `DbSnapshot` as built (§7.2): the pass reports it and tries again next time. Tolerating growth soundly costs more round trips and waits for the first provider that needs it.
- **Many small segments.** A session synced while it is active gains a segment per pass. Harmless for correctness; compaction is listed for later.
- **The same conversation in two sessions.** Resuming or forking can copy earlier history into a new transcript file, so text is archived twice and search shows both. Linking them is listed for later.
- **Found in the shared stack while building,** to fix in toolbox-rs or gpui rather than here: on Windows, closing the window logs a few `Invalid window handle` errors to stderr (dv does the same; the exit code is 0); the automation host treats a line of invalid UTF-8 on stdin as quit, and a `resize` to an absurd size aborts the app; on macOS gpui writes one preference file for the app at launch, outside the data folder.
- **Two apps on one archive** are prevented by the lock (§4.4). A read-only second opener is not planned.
- **Secrets.** Transcripts contain whatever the agent saw. The archive is not encrypted (FEATURES: out of scope); it is as private as its folder.
- **One archive per machine.** Each machine the app is opened on has its own archive; they are independent until merging exists (FEATURES: Later).
- **Lost answer tails on WSL** (§6.2): under load, about one call in 1,000–1,500 loses the end of its answer right after the login shell's output, with exit status 0 and nothing on stderr. Closing an extra descriptor doesn't help. The one-time retry covers it: in a soak of nine processes over an hour, about 21,000 `env` calls and 3,000 sync passes, nothing failed and the archives verified byte for byte against the distro. Where it happens: in every lost answer the outer shell ran to its last line, so the bytes are written and then lost in `wsl.exe`'s relay, at the moment the backgrounded login shell (a second writer of the answer) exits. A plain `sh -c` in its place loses at the same rate, so profiles aren't the cause. No variant removed it: keeping the login shell in the outer shell's session made it worse, and routing its output through `cat` (or dropping the watchdog) made it rarer, but not gone. Under ordinary load it is rarer still (about 1 in 2,500 calls). **Decided (owner):** the retry is the fix; the `cat` layouts are not pursued. `read_ranges` is never retried, but it runs after the environment is read and has no second writer.
- **Hostile transcripts.** The reader's bounds are structural (§9) and were attacked over seven rounds; the worst measured costs in release are about 200 ms for one Markdown region and 70 ms for one highlighted block, all off the UI thread. They were measured on macOS; Windows is checked in the port pass. Highlighting is still in-process: a grammar whose C code aborts takes the app with it, so `grammars_never_abort` is run by hand whenever grammars change.
- **Uninstalling on Windows is unverified on a real machine.** v0.1.0's install, update check and feed were checked on the owner's PC; uninstalling was not, since that copy is in use. What protects the archive is the pack id (`scrollback-app`) being apart from the data folder (`scrollback`), held by a test, and Settings refusing an archive inside the install folder. Verify an uninstall on a spare machine or VM before relying on it.
- **WSL details to check on the PC:** the distro's default user and `$HOME`, a custom mount root in `/etc/wsl.conf`, `wsl.exe`'s behaviour when the distro is stopped or WSL is updating.
